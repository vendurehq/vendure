Vendure uses a multi-stage pipeline to determine the price a customer actually pays. Rather than storing a single "final" price, the system starts with a base price and transforms it step-by-step through strategies, promotions, and tax calculations. This makes it possible to support complex scenarios like channel-specific pricing, dynamic discounts, and tax-inclusive or tax-exclusive display.

## The price pipeline

When an item is added to an order, Vendure resolves its price through the following stages:

1. **ProductVariantPrice** — The base price stored in the database. Each [`ProductVariant`](/reference/typescript-api/entities/product-variant/) has one or more [`ProductVariantPrice`](/reference/typescript-api/entities/product-variant-price/) records, scoped by channel and currency.
2. **ProductVariantPriceSelectionStrategy** — Selects which `ProductVariantPrice` to use when multiple prices exist for the active channel and currency.
3. **ProductVariantShopperPriceStrategy** — Determines the unit price for the shopper and the quantity, and whether it includes tax. This is the main extension point for custom pricing logic such as customer-specific pricing, tiered pricing, or time-based deals. See [The shopper price](#the-shopper-price).
4. **OrderItemPriceCalculationStrategy** — Determines the unit price of the order line. The default uses the shopper price. Use it for logic that needs the order or the order line.
5. **Promotions** — Any active [promotions](/core-concepts/promotions/) that apply order-level or item-level discounts are calculated and applied as adjustments.
6. **Tax calculation** — The applicable tax rate is determined (based on [tax category, zone, and strategy](/core-concepts/taxes/)) and applied to produce the final tax-inclusive price.

The result of this pipeline is exposed in the GraphQL API as a pair of fields on every taxable price: a **base** field and a **WithTax** field. For example, an `OrderLine` exposes `linePrice` and `linePriceWithTax`, and the `Order` itself exposes `subTotal` / `subTotalWithTax`, `total` / `totalWithTax`, and so on.

## The shopper price

`ProductVariant.price` and `priceWithTax` give the price of the channel. The price that a shopper pays can depend on more: the customer, the quantity, or input that the cart stores in order line custom fields. The [`ProductVariantShopperPriceStrategy`](/reference/typescript-api/products-stock/product-variant-shopper-price-strategy/) calculates this unit price. It receives the variant with the channel price applied, and returns the unit price for a shopper and a quantity, with no order.

Vendure uses the strategy in two places:

- In the cart, the default `OrderItemPriceCalculationStrategy` calls it for each order line, for the customer of the order. In an Admin draft order, this is the customer of the order, not the administrator.
- In the Shop API, the `ProductVariant.shopperPrice` field calls it for the active customer. A storefront can show the price that the cart will use.

```graphql
query {
    product(slug: "laptop") {
        variants {
            id
            price
            priceWithTax
            shopperPrice(quantity: 10) {
                price
                priceWithTax
            }
        }
    }
}
```

If you define custom fields on `OrderLine`, the field also has a `customFields` argument of the type `OrderLineCustomFieldsInput`. Pass the same values as to `addItemToOrder`. For example, a storefront that sells by packaging unit passes the unit code to both, and gets the same price on the product page and in the cart.

### Writing a shopper price strategy

Add your logic as a [`StrategyLayer`](/reference/typescript-api/configuration/strategy-layer/) over the configured strategy:

```ts title="src/plugins/customer-prices/customer-price-layer.ts"
import {
    PriceCalculationResult,
    ProductVariant,
    ProductVariantShopperPriceArgs,
    ProductVariantShopperPriceStrategy,
    RequestContext,
    StrategyLayer,
} from '@vendure/core';

export class CustomerPriceLayer extends StrategyLayer.passThrough<ProductVariantShopperPriceStrategy>() {
    static priority = 100;

    async calculateUnitPrice(
        ctx: RequestContext,
        productVariant: ProductVariant,
        args: ProductVariantShopperPriceArgs,
    ): Promise<PriceCalculationResult> {
        const result = await this.inner.calculateUnitPrice(ctx, productVariant, args);
        const customer = await args.getCustomer();
        if (!customer) {
            return result;
        }
        // Look up the price of this customer, for example in a custom entity
        return result;
    }
}
```

```ts title="src/vendure-config.ts"
import { composeStrategy, DefaultProductVariantShopperPriceStrategy, VendureConfig } from '@vendure/core';

import { CustomerPriceLayer } from './plugins/customer-prices/customer-price-layer';

export const config: VendureConfig = {
    // ...
    catalogOptions: {
        productVariantShopperPriceStrategy: composeStrategy(
            CustomerPriceLayer,
            new DefaultProductVariantShopperPriceStrategy(),
        ),
    },
};
```

Things to know:

- `args.getCustomer()` loads the customer only when you call it. With the default strategy, the `shopperPrice` field runs no extra database query.
- Do not write to `args.orderLineCustomFields`. For the `shopperPrice` field it is a copy of the request input. To store data on the order line, use the `OrderItemPriceCalculationStrategy`.
- Vendure does not cache the result. The `shopperPrice` field runs the strategy once for each variant that requests the field. If your strategy is slow, for example because it calls an external system, it must cache the results itself.
- The field uses the tax zone of the session, as `priceWithTax` does. The cart uses the tax zone of the order, which can come from the shipping address. When the two zones differ, `shopperPrice.priceWithTax` can differ from the `unitPriceWithTax` of the order line.
- In code, use `ProductVariantService.calculateShopperPrice()`.

### Shopper price or order item price?

The `OrderItemPriceCalculationStrategy` gives the price of an order line, and it has the order. Use it only for logic that needs the order, or that writes data to the order line. Put logic that depends on the variant, the customer, the quantity and the order line custom fields in the shopper price strategy. Then the storefront and the cart show the same price.

A custom `OrderItemPriceCalculationStrategy` that replaces the default must call `productVariantShopperPriceStrategy` for its base price. Otherwise the cart ignores the shopper price strategy. If you have a custom `OrderItemPriceCalculationStrategy` today, move the logic that does not need the order into a shopper price layer, and write the rest as a `StrategyLayer` over the default `OrderItemPriceCalculationStrategy`.

## Channel-specific pricing

Because [`ProductVariantPrice`](/reference/typescript-api/entities/product-variant-price/) records are scoped to a specific [channel](/core-concepts/channels/) and currency, the same product variant can have entirely different prices in different channels. This is essential for multi-region or multi-vendor setups where each storefront operates with its own currency and pricing structure.

A single variant might have a price of $30 USD in the US channel and 25 GBP in the UK channel. If a channel supports multiple currencies, the variant can even have more than one price within that channel.

## The `price` vs `priceWithTax` convention

Throughout the Vendure GraphQL APIs, monetary values always come in pairs:

- **`price`** — The amount _without_ tax (or the tax-inclusive amount if the channel is configured for tax-inclusive pricing, in which case tax has been back-calculated).
- **`priceWithTax`** — The amount _with_ tax included.

This convention applies to individual line items, order subtotals, shipping costs, and the order total. Your storefront can choose which value to display based on local regulations and conventions.

:::info
All monetary values in Vendure are stored as **integers in the smallest currency unit** (e.g., cents for USD). See [Money & Currency](/core-concepts/money/) for details on how Vendure handles monetary arithmetic.
:::

## Promotions and adjustments

After the base price is resolved, Vendure applies any qualifying [promotions](/core-concepts/promotions/). Promotions never modify the base price directly. Instead, they add **adjustments** to the order or order line, which are tracked separately. This means the original price is always preserved, and discounts can be clearly itemized for the customer.

There are two levels of adjustment:

- **Order-level adjustments** — Applied to the order as a whole, such as "10% off your entire order" or "$5 off when you spend over $50".
- **Item-level adjustments** — Applied to individual order lines, such as "buy one get one free" on a specific product.

Both types are stored alongside the order and are visible in the API, so your storefront can show the customer exactly which discounts were applied and how much they saved.

## Extending the pipeline

The pricing pipeline is designed to be customized at each stage. The two most common extension points are:

- **ProductVariantShopperPriceStrategy** — For scenarios where the price depends on runtime context such as the logged-in customer, the quantity, or external data.
- **ProductVariantPriceSelectionStrategy** — For controlling which stored price is selected when multiple options exist.

Both strategies are configured at the server level and apply globally. For details on implementing custom strategies, see the [TypeScript API reference](/reference/typescript-api/products-stock/product-variant-shopper-price-strategy/) and [The shopper price](#the-shopper-price).
