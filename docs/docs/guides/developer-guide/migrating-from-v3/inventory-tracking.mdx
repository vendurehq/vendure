Vendure v4 lets you track inventory for some channels or stock locations and not others. The global setting is gone, and the channel decides instead.

<Callout type="warning">
Upgrade with `synchronize: false` and run the data migration from your v4 migration. Vendure v4 refuses to start until it has run.
</Callout>

## What changes

Whether inventory is tracked is resolved most specific first:

1. **`StockLevel.trackInventory`**: one variant at one stock location. New in v4, defaults to `INHERIT`.
2. **`ProductVariant.trackInventory`**: unchanged.
3. **`Channel.trackInventory`**: the default for everything set to `INHERIT`. The field existed in v3, but Vendure never read it.

`GlobalSettings.trackInventory` is removed from the Admin API. For anything to do with an Order (allocation, fulfillment, cancellation, modification), the Order's own Channel decides, even when an Administrator acts from another Channel.

Each stock movement now records whether it changed the stock figures (`StockMovement.tracked`). If a tracking setting changes while Orders are open, their remaining releases, sales and cancellations still follow the setting that applied when their stock was allocated.

## Migrating the data

The migration copies the v3 `GlobalSettings.trackInventory` value to every Channel, so every variant keeps its current behaviour. It also fills `StockMovement.tracked` for the stock movements recorded before the upgrade, using the v3 rule, so Orders that are open during the upgrade are released and fulfilled as they were allocated.

### With migrations

Call both helpers from your v4 migration, **after** the generated statements:

```ts
import { backfillStockMovementTracking, migrateTrackInventoryToChannels } from '@vendure/core';

export class V4Upgrade1234567890 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<any> {
        // --- Auto-generated DDL ---
        // ...

        // --- Data-migration helpers ---
        await migrateTrackInventoryToChannels(queryRunner);
        await backfillStockMovementTracking(queryRunner);
    }
}
```

[`migrateTrackInventoryToChannels`](/reference/typescript-api/migration/migrate-track-inventory-to-channels) throws if it is called before the generated statements, and if it cannot find the `global_settings` table. Both helpers honour the `entityPrefix` of your connection options and, on PostgreSQL, the `schema` option.

### With `synchronize: true`

Set `dbConnectionOptions.synchronize` to `false` for the upgrade, and run the helpers from a migration as described above. You can switch `synchronize` back on afterwards.

If you leave `synchronize` on, no data is lost: Vendure keeps the v3 column (`global_settings.trackInventory`) until the helper has copied it.

### Startup check

Until the value has been copied, Vendure v4 refuses to start. Otherwise each Channel's stored `trackInventory`, which v3 ignored and which is usually `true`, would take effect at once. A shop which did not track inventory would start allocating stock it never maintained, and limiting sales by it.

### During a rolling deployment

A v3 server which saves the Global Settings writes the v3 column again, and the next v4 server then refuses to start. Do not edit the Global Settings from a v3 Dashboard once the migration has run. If it happens, run `migrateTrackInventoryToChannels` again.

## After migrating

- **Channels whose value was overwritten.** A Channel's stored `trackInventory` had no effect in v3, so the migration overwrites it with the global value. The helper logs each Channel whose value differed. If you had set those on purpose, set them again.
- **New Channels** are tracked by default (`trackInventory: true`). If your shop did not track inventory, set it when you create a Channel.
- **Search index.** The default search plugin reindexes a Channel when its `trackInventory` changes. Other search plugins may need a manual reindex.

## Updating your code

| If your code… | Do this |
|---|---|
| Reads or writes `GlobalSettings.trackInventory` (Admin API, `GlobalSettingsService`, the entity) | Use `Channel.trackInventory`. Per variant and location, use `ProductVariant.trackInventory` and `StockLevel.trackInventory`. |
| Decides whether a variant is tracked from `variant.trackInventory` alone | Use `StockLevelService.isInventoryTracked(ctx, variant, stockLevel?)`, or the Admin API's resolved `ProductVariant.tracksInventory` and `StockLevel.tracksInventory`. A StockLevel can override the variant. |
| Implements or extends `StockLocationStrategy` | `getAvailableStock()` gets an optional fourth argument, the variant, and should report `hasUntrackedStock`. Results of `forAllocation()` and the other methods can say whether each part is `tracked`. To apply your own tracking rules, implement `isInventoryTracked()`. |
| Calls `DefaultStockLocationStrategy.getAvailableStock()` with three arguments | It now returns a Promise. Await it, or pass the variant. |
| Subscribes to `StockMovementEvent` (for example an ERP sync) | One movement can be split into a tracked and an untracked row. Read `StockMovement.tracked`, not the variant setting. |
| Has a custom `FulfillmentProcess` copied from the default one | When a Fulfillment is cancelled, call `stockMovementService.reverseSalesForOrderLines()` instead of `createCancellationsForOrderLines()` followed by `createAllocationsForOrderLines()`. |
| Sends `StockLevelInput` in `updateProductVariants` | `stockOnHand` is optional, so you can change `trackInventory` without writing the stock. |
| Sends `trackInventory` in every `updateChannel` call | Send it only when it changes. Each call that includes it reindexes the Channel in the default search plugin. |
| Adds `trackInventory` to `StockLevel` or `StockLevelInput` through an API extension | Remove the extension. The field is part of the schema now. |
