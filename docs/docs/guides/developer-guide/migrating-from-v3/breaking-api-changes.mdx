This page lists the v4 changes that break plugins, custom code and Admin API clients. Run the codemods first, then search for the code they do not change, then work through the sections that apply to your project.

## Codemods

| Codemod | Change |
|---|---|
| `npx vendure codemod role-assignments [path]` | [Role assignments](/developer-guide/migrating-from-v3/role-assignments#running-the-codemod) |

A codemod makes the edits that have one right answer. Where the replacement depends on what your code is meant to do, it adds a `// TODO(vendure-v4):` comment naming the replacement instead.

**Done when:** each codemod has run, and `rg "TODO\(vendure-v4\)"` lists only comments you still have to work through.

## Finding code to update

The codemods do not change the code below. Search your project for each pattern and update every match.

```bash
rg -n "RoleChangeEvent|getCustomerRole|getChannelsForRole|assignRoleToChannel|assertActiveUserCanGrantRoles"
rg -n "CUSTOMER_ROLE_CODE|CUSTOMER_ROLE_DESCRIPTION|user_roles_role|role_channels_channel"
rg -n "createApiKeyUser\(|createAdministratorAndUser\(|implements SessionCacheStrategy"
rg -n "roleIds" -g "*.graphql" -g "*.ts" -g "*.tsx"
rg -n "trackInventory|outOfStockThreshold|StockLocationStrategy|getAvailableStock\(|createCancellationsForOrderLines"
rg -n "ApiPlayground|ApiDebug|healthChecks|HealthCheck|HealthIndicator|TaxRateModificationEvent|TtlCache"
rg -n "customFulfillmentProcess|customPaymentProcess|Custom(Order|Payment|Fulfillment|Refund)(Process|States)"
rg -n "getOrderFromContext|addPromotionsToOrder|deleteGroupAndOptionsFromProduct|\.isAuthorized\b"
rg -n "useExperimentalBundle|tanstackRouterPluginOptions|from '@/(vdb|graphql)/"
rg -n "productVariantPrices|implements ProductVariantPrice(Selection|Calculation)Strategy"
```

| Match | What to do |
|---|---|
| `RoleChangeEvent` | Subscribe to `RoleAssignmentEvent`. See [Events](/developer-guide/migrating-from-v3/role-assignments#events). |
| `trackInventory`, `outOfStockThreshold`, `StockLocationStrategy`, `getAvailableStock(`, `createCancellationsForOrderLines` | See [Updating your code](/developer-guide/migrating-from-v3/inventory-tracking#updating-your-code). |
| `getCustomerRole`, `CUSTOMER_ROLE_CODE`, `CUSTOMER_ROLE_DESCRIPTION` | Remove. There is no Customer role. See [Customers](/developer-guide/migrating-from-v3/role-assignments#customers). |
| `getChannelsForRole`, `assignRoleToChannel`, `assertActiveUserCanGrantRoles`, `createApiKeyUser(`, `createAdministratorAndUser(` | See [Services](/developer-guide/migrating-from-v3/role-assignments#services). |
| `user_roles_role`, `role_channels_channel` in SQL | Query the `role_assignment` table. See [Entities](/developer-guide/migrating-from-v3/role-assignments#entities). |
| `implements SessionCacheStrategy` | Check that it stores `globalPermissions`. See [Sessions and permission checks](/developer-guide/migrating-from-v3/role-assignments#sessions-and-permission-checks). |
| `roleIds` in Admin API calls | Works on the active Channel only. Move multi-channel clients to `assignRolesToUser`. See [Admin API](/developer-guide/migrating-from-v3/role-assignments#admin-api). |
| Anything matched by the three searches before the last | See [Removed deprecated APIs](#removed-deprecated-apis). |
| `useExperimentalBundle`, `tanstackRouterPluginOptions`, imports from `@/vdb/` or `@/graphql/` | See [The Dashboard is served from its pre-built bundle](#the-dashboard-is-served-from-its-pre-built-bundle). |
| `productVariantPrices`, a custom `ProductVariantPriceSelectionStrategy` or `ProductVariantPriceCalculationStrategy` | See [ProductVariant prices are loaded per Channel](#productvariant-prices-are-loaded-per-channel). |

**Done when:** every match is updated, and `npx tsc --noEmit` passes.

## Role assignments

`User.roles` and `Role.channels` are removed, and Roles are granted per Channel through `RoleAssignment` rows. The main breaks:

- Read a User's Roles with `RoleAssignmentService.resolveUserRoles()`, and grant or revoke them with `RoleAssignmentService.assign()` / `remove()`.
- `RoleChangeEvent` is replaced by `RoleAssignmentEvent`. The codemod does not rewrite it.
- `RoleService.getCustomerRole()` is removed. There is no Customer role.
- Every Role is owned by the Channel it was created on. A Role owned by the default Channel can be assigned on any Channel; any other Role only on its owning Channel.
- In the Admin API, `Role.channels` and `channelIds` on the Role inputs are removed, and `Role.channel` returns the owning Channel. `createRole` creates the Role on the active Channel. The deprecated `roleIds` inputs now apply to the active Channel only. Use `assignRolesToUser` and `removeRolesFromUser` instead.
- Role CRUD needs the new `CreateRole`, `ReadRole`, `UpdateRole` and `DeleteRole` permissions on the Channel that owns the Role.
- An API key cannot be granted the SuperAdmin Role, or Roles on Channels it does not belong to.
- An Administrator cannot delete themselves or remove their own last role assignment.
- `BaseAuthResolver.publiclyAccessibleUser()` takes the `RequestContext` as its first argument. Only relevant if you extend the auth resolvers.

For the full list, and what stays the same, see [Updating your code](/developer-guide/migrating-from-v3/role-assignments#updating-your-code).

## Order item pricing

The default cart pricing now uses the [buyer price](/core-concepts/pricing/#the-buyer-price). Without custom strategies, the prices do not change.

- `DefaultOrderItemPriceCalculationStrategy` needs `init()`. Vendure calls it for the configured strategy. If your code creates the strategy with `new` and calls `calculateUnitPrice()` directly, call `init(injector)` first.
- When the customer of an active order or a draft order changes, Vendure calculates the price of all lines again, so a custom `OrderItemPriceCalculationStrategy` now also runs for `setCustomerForOrder`, `setCustomerForDraftOrder`, `setOrderCustomer` and the login of a guest. A line that has no price for the new customer keeps its current price.
- `OrderItemPriceCalculationStrategy.calculateUnitPrice()` has an optional last argument, `options?: { buyer?: Buyer }`. Vendure does not pass it, so existing strategies work without changes. A `StrategyLayer` can pass `options.buyer` to `inner`, and the default strategy then prices the line for that buyer and not for the customer of the order. A custom strategy that calls `calculateBuyerPriceForOrder()` should pass `buyer: options?.buyer` to it. A layer that calls `inner` with its own argument list should pass `options` on. See [the buyer](/core-concepts/pricing/#the-buyer).
- `DefaultOrderItemPriceCalculationStrategy` is now exported from `@vendure/core`. You can extend or wrap it directly.

## ProductVariant prices are loaded per Channel

`ProductVariant.productVariantPrices` is no longer an eager relation. In v3, every variant Vendure loaded came with one price row per Channel it is assigned to, although a request only needs the rows of its own Channel. With many Channels these rows were most of what a product page, a cart or a checkout read.

Now, when a variant is priced, the [`ProductPriceApplicator`](/reference/typescript-api/service-helpers/product-price-applicator) loads the prices of the active Channel, for all variants priced together in one query. The GraphQL APIs return the same prices as before.

What breaks:

- **Code which reads `variant.productVariantPrices`** after loading a variant with the `TransactionalConnection`, a repository or the `EntityHydrator`, or from an entity event, finds it `undefined` unless the query requested the relation. Request it (`relations: { productVariantPrices: true }`), or call `ProductVariantService.getProductVariantPrices(ctx, variantId)`, which returns the prices of the active Channel.
- **A custom `ProductVariantPriceSelectionStrategy` or `ProductVariantPriceCalculationStrategy`** now sees only the prices of the active Channel, unless the variant was loaded with others. A strategy which falls back to the price of another Channel, such as the default Channel, has to load that price itself, for example with the `TransactionalConnection` from the `Injector`.
- **Constructor:** `ProductPriceApplicator` takes a `TransactionalConnection` as its last argument. This only matters if you create it with `new` or subclass it with your own constructor.

Saving a priced variant leaves the prices of its other Channels in place, even though the variant carries only those of the active Channel.

Sorting or filtering a variant list by `price` or `priceWithTax` now uses the prices of the active Channel in the active currency. In v3 it used the prices of every Channel, so a list could be out of order when a variant cost more in one Channel than another.

Code which prices variants with `ProductPriceApplicator.applyChannelPriceAndTax()` or `ProductVariantService.applyChannelPriceAndTax()` needs no change. When you price variants one after another in a loop, call `ProductPriceApplicator.preloadChannelPrices(ctx, variants)` first, so their prices are loaded in one query rather than one per variant.

`ProductVariantService.getFacetValuesForVariant()` now returns only the FacetValues of the active Channel, and no longer loads their `channels`. This is not exposed in GraphQL. To read the Channels of a FacetValue, load it with `relations: ['channels']`, for example with `TransactionalConnection.getEntityOrThrow()`.

## Inventory tracking

Inventory tracking is resolved per stock level, then per variant, then per channel. The main breaks:

- `GlobalSettings.trackInventory` and `UpdateGlobalSettingsInput.trackInventory` are removed from the Admin API. Use `Channel.trackInventory`. The value is copied by the `migrateTrackInventoryToChannels` migration helper.
- `GlobalSettings.outOfStockThreshold` and `UpdateGlobalSettingsInput.outOfStockThreshold` are removed from the Admin API. A variant with `useGlobalOutOfStockThreshold` uses `Channel.outOfStockThreshold`. The value is copied by the `migrateOutOfStockThresholdToChannels` migration helper.
- `ProductVariant.trackInventory` is the variant's default, not the final answer: a `StockLevel.trackInventory` can override it. Use `StockLevelService.isInventoryTracked()` or the resolved `tracksInventory` fields of the Admin API.
- `StockLocationStrategy.getAvailableStock()` takes the variant as an optional fourth argument and should report `hasUntrackedStock`. `DefaultStockLocationStrategy.getAvailableStock()` returns a Promise when called with three arguments.
- `StockMovementEvent` subscribers can receive a movement split into a tracked and an untracked row.

For the full list, see [Updating your code](/developer-guide/migrating-from-v3/inventory-tracking#updating-your-code).

## Shipping options

A ShippingMethod can now offer several priced [shipping options](/core-concepts/shipping/#several-options-per-shippingmethod), such as the services of a carrier API. Existing ShippingCalculators keep working unchanged. What can break:

- **Code which builds `ShippingMethodQuote` or `TestShippingMethodResult` objects**, such as a custom resolver or a plugin that returns its own shipping quotes, must set the new non-null `options` field. The generated TypeScript types require it. For a quote with one price, return one option with a null `code` and the quote's `price`, `priceWithTax` and `metadata`.
- **`setOrderShippingMethod(shippingMethodId)`** is now optional, because the new `shippingMethods` argument can be passed instead. Exactly one of the two must be given. Generated TypeScript types for the mutation's arguments change accordingly.
- **A ShippingMethod whose calculator returns no result** can no longer be set on an Order: `setOrderShippingMethod`, `setDraftOrderShippingMethod` and `modifyOrder` return an `IneligibleShippingMethodError`. In v3 such a method could be set, and its ShippingLine stayed at a price of 0. It was already left out of `eligibleShippingMethods`. When the calculator of a ShippingLine's method returns no result as the Order is recalculated, the ShippingLine now falls back to the cheapest eligible option, as for an ineligible method. In v3 it kept its previous price.
- **`modifyOrder` with `recalculateShipping: false`** now prices a ShippingMethod it sets with the chosen option's price, and applies the shipping promotions to that price. In v3 the ShippingLine kept the price of the previous method.
- **`setOrderShippingMethod` and `setDraftOrderShippingMethod` leave the Order in the database as it was when they return an error.** They run in a savepoint of the request's transaction, which is rolled back when the method or option is refused. Events published by promotion side effects while the Order was priced are not undone.
- **`OrderService.setShippingMethod()` and `OrderModifier.setShippingMethods()`** accept a `ShippingMethodSelectionInput` as well as an ID for each entry. An empty list is refused.
- **`OrderModifier.setShippingMethods()`** returns a `SetShippingMethodsResult` with the `order` and a `selectionKept()` function rather than the Order itself. As before, it does not price the ShippingLines: recalculate the Order afterwards, then pass its ShippingLines to `selectionKept()` to find out whether a selected option was refused. `OrderService.setShippingMethod()` does both.
- **`ShippingLine`** has two new nullable columns, `shippingOptionCode` and `shippingOptionName`. The generated migration adds them.

## Tax rates

A TaxRate can now target a country as well as a Zone, and a country rate wins over a zone rate. See [Tax rate resolution](/core-concepts/taxes/#tax-rate-resolution). Existing zone rates keep their Zone and resolve as before. What can break:

- **`TaxRate.zone` is nullable** in the GraphQL APIs and on the entity (`zone?: Zone | null`, `zoneId?: ID | null`), because a country rate has no Zone. Code which reads `taxRate.zone.id` or `taxRate.zone.name` must handle `null`. The new `region` field holds the country of a country rate.
- **`CreateTaxRateInput.zoneId` is optional.** Exactly one of `zoneId` and the new `regionId` must be set. Generated TypeScript types for the input change accordingly.
- **`TaxRateService.getApplicableTaxRate()`** takes `{ countryCode, zone }` as its second argument, so that a country rate can be found. Passing a Zone or zone ID still works, but then only zone rates are found. To apply country rates in your own code, pass the country of the Order's shipping address as `countryCode`.
- **`tax_rate`** has a new nullable column, `regionId`, and **`order`** a new nullable column, `taxCountryCode`. The generated migration adds them. `Order.taxCountryCode` records the tax country of the last tax calculation, which by default is the shipping country. An Order placed before v4 has none. Its next calculation records the country and keeps the taxes the Order was placed with.

These additions need no change to your code:

- **`TaxZoneStrategy.determineTaxCountryCode()`** is a new optional method, which chooses the country whose country rates apply. Without it, the country of the shipping address is used, as above. The new **`defaultTaxCountryCode()`** function exports that default, so a strategy can keep it for some cases. See [Choosing the tax country](/core-concepts/taxes/#choosing-the-tax-country).
- **`Channel.taxCountryCode`** is a new optional field, the country whose rate the Channel's tax-inclusive prices include. **`channel`** has a new nullable column, `taxCountryCode`. The generated migration adds it. Channels that leave it unset behave as before, and `defaultTaxZone` keeps all its roles. **`TaxRateService.findIncludedTaxRate()`** returns the included rate, and `DefaultProductVariantPriceCalculationStrategy` uses it. See [The Channel's tax country](/core-concepts/taxes/#the-channels-tax-country).
- In a Channel whose prices include tax, when the tax Zone or the tax country of an active Order changes, every OrderLine is now priced again, as on a currency change, because its net price depends on the rate. Before, only the lines being edited were. The line's `initialListPrice` is converted between gross and net the same way, so the `ChangedPriceHandlingStrategy` is only called when the merchant changed the price. Order modifications keep the prices of the lines they do not change.

## Changed defaults

Some defaults which were kept for compatibility during v3 have changed. Set the old value to keep the v3 behaviour.

### CORS allows no cross-origin requests

`apiOptions.cors` now defaults to `{ origin: false, credentials: true }` (it was `{ origin: true, credentials: true }`, which let any website make credentialed requests to both APIs). The server sends no `Access-Control-Allow-Origin` header, so a browser only lets pages on the server's own origin call the API.

Projects created with `@vendure/create` 3.7.3 or later set `cors` themselves and are not affected. Projects created with an earlier version do not, so check your config for a `cors` entry. If it does not set `cors`, these break:

- a storefront that calls the API from the browser on a different origin, including a different port in local development
- the Dashboard Vite dev server, when you open it directly rather than through the `DashboardPlugin`
- an Admin UI or Dashboard hosted on a separate domain
- browser calls to other routes on the server from another origin. `apiOptions.cors` applies to the whole server, so this includes plugin REST controllers, assets fetched from script, and the MCP plugin's `/mcp` and OAuth endpoints

Server-side requests, for example from a server-rendered storefront, and the Dashboard served by the `DashboardPlugin` are not affected. List the origins your browsers call the API from:

```ts
apiOptions: {
    cors: {
        origin: ['https://storefront.example.com', 'http://localhost:3001'],
        credentials: true,
    },
},
```

Setting `origin: true` restores the v3 behaviour. Use it only in local development. See [Configure CORS](/developer-guide/security/#configure-cors).

### CSRF prevention is on

`apiOptions.csrfPrevention` now defaults to `true` (it was `false`). The Shop and Admin APIs reject a request whose content type is `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`, and any `GET` request, unless it sends an `Apollo-Require-Preflight` or `x-apollo-operation-name` header. This stops a cross-site HTML form from logging a visitor in as someone else (Login CSRF).

Requests sent as `application/json` are unaffected. `@vendure/dashboard` and `@vendure/testing` already send the header. Check:

- clients that upload files, for example a custom admin client built on `apollo-upload-client`: send `Apollo-Require-Preflight: true`
- storefronts that send queries as `GET` for caching: send `Apollo-Require-Preflight: true`

If a client cannot send either header, name a header it already sends, for example `csrfPrevention: { requestHeaders: ['x-my-client-header', 'apollo-require-preflight'] }`. Setting `csrfPrevention: false` restores the v3 behaviour, and Vendure logs a warning at startup. See [CSRF prevention](/developer-guide/security/#csrf-prevention).

### DefaultSearchPlugin indexes stock status and currency

`indexStockStatus` and `indexCurrencyCode` now default to `true`, also when the plugin is used without `init()`. The `search` query gets the `inStock` field and filter, and returns prices in the currency of the request in Channels with more than one currency.

This changes the `search_index_item` table: it gets the `inStock` and `productInStock` columns, and `currencyCode` joins its primary key. The search index only holds data derived from your catalog, so in the generated migration, empty the table before the new columns are added (`DELETE FROM search_index_item`), and run a full reindex after deploying.

To keep the v3 table and behaviour:

```ts
DefaultSearchPlugin.init({ indexStockStatus: false, indexCurrencyCode: false });
```

### DefaultJobQueuePlugin buffers jobs in the database

`useDatabaseForBuffer` now defaults to `true`, so buffered jobs (for example the search index updates of `bufferUpdates`) are stored in the `job_record_buffer` table. They survive a restart and are shared by every server instance. The generated migration creates the table. A `jobBufferStorageStrategy` you configured yourself is kept. To keep the in-memory buffer, set `DefaultJobQueuePlugin.init({ useDatabaseForBuffer: false })`.

### Passwords need 8 characters

The `DefaultPasswordValidationStrategy` in the default config now has a `minLength` of `8` (it was `4`). It applies when a Customer's password is set: on registration and verification, on password changes and resets, and when a Customer is created with a password. Existing passwords keep working. To keep the v3 rule:

```ts
authOptions: {
    passwordValidationStrategy: new DefaultPasswordValidationStrategy({ minLength: 4, maxLength: 72 }),
},
```

The `testConfig` of `@vendure/testing` keeps a `minLength` of `4`, so test fixtures with short passwords keep working.

### Dashboard detail pages send only changed fields

`useDetailPage` and the `DetailPage` component now default `sendOnlyChangedFields` to `true`: an update mutation receives `id`, the top-level fields the user changed and any non-nullable fields, rather than the whole form. This stops a page from overwriting a field that someone else changed since the page was loaded.

An update mutation of your own must leave an absent field unchanged, which it does if it uses `patchEntity()` or the `TranslatableSaver`. If it treats an absent field as empty, or derives a stored value from several input fields, set `sendOnlyChangedFields: false` on the page. A `transformUpdateInput` function now receives the partial input, and subscribers to entity events see the partial input in `event.input`.

`updatePromotion` now computes the priority score from the stored conditions and actions when the input omits them. Before, an update without `conditions` and `actions` reset the score to 0.

### Order modifications keep the discounts of a paid Order

`modifyOrder` no longer re-tests every Promotion on every modification. The new `orderOptions.promotionFreezeStrategy` decides, and the default `DefaultPromotionFreezeStrategy` freezes the Promotions unless the modification changes the OrderLines, the coupon codes or the shipping methods. So an address change, a surcharge, a note or a custom field no longer changes what a paid Order costs, even if a Promotion has been disabled since payment or one of its conditions now answers differently. In v3 it could.

- The `freezePromotions` option of `ModifyOrderInput.options` was never read in v3. It now overrides the strategy: `true` keeps the discounts, `false` re-tests the Promotions.
- When the Promotions are frozen, the OrderLines keep their discount amounts, so units added to an existing line get no discount. Lowering a line's quantity scales its discount down in proportion. A shipping discount is capped at the new shipping price.
- A modification that changes the coupon codes while the Promotions are frozen is rejected.
- Coupon codes that are already on the Order are no longer validated again. In v3, re-sending a code whose Promotion had been disabled or had ended returned `CouponCodeInvalidError` or `CouponCodeExpiredError`, and a code with a per-customer usage limit could return `CouponCodeLimitError` because the Order counted against itself. Now the modification goes ahead. New codes are still validated.
- When the Promotions are re-tested, the ones already on the Order are candidates too, so a Promotion disabled since payment still applies as long as its conditions pass.
- The `ORDER_MODIFIED` history entry records the decision in `data.promotionsFrozen`.
- The Dashboard previews a modification both ways. When the discounts would differ, the administrator chooses which ones the Order gets.

To re-test the Promotions on every modification unless the client asks to freeze them, which is closest to v3:

```ts
import { PromotionFreezeStrategy } from '@vendure/core';

orderOptions: {
    promotionFreezeStrategy: {
        shouldFreezePromotions: (ctx, order, input) => input.options?.freezePromotions === true,
    } satisfies PromotionFreezeStrategy,
},
```

## The Dashboard is served from its pre-built bundle

`vendureDashboardPlugin` now always loads the Dashboard from the pre-built bundle in the `@vendure/dashboard` package, which was opt-in through `useExperimentalBundle` since v3.7. Your Vite dev server no longer compiles the Dashboard's own source. This cuts the number of module requests on a cold load from about 3,000 to about 40.

- Remove `useExperimentalBundle` and `tanstackRouterPluginOptions` from your `vite.config`. The bundle already contains the Dashboard's routes, so the TanStack Router plugin no longer runs in your project, and no longer writes `routeTree.gen.ts` into `node_modules`.
- Hot module replacement still works for your Dashboard extensions. Changes to the Dashboard's own files inside `node_modules` are no longer picked up.
- Import everything from `@vendure/dashboard`. Imports from the `@/vdb/*` and `@/graphql/*` aliases are deprecated. They still resolve, but now to `@vendure/dashboard`, and log a warning. An import of something that `@vendure/dashboard` does not export fails with a "missing export" error. The aliases will be removed in v5.
- Remove the `@/vdb/*` path from your `tsconfig.json`. `@vendure/dashboard` now ships type declarations, so TypeScript no longer reads the Dashboard's source.
- The package no longer ships the Dashboard's TypeScript source. Code that reads files from `node_modules/@vendure/dashboard/src` must import from `@vendure/dashboard` instead.

## CLI login API

The Vendure CLI signs in with a device login, so the browser login API that `@vendure/cli` exported since v3.8.0 is removed. It was not deprecated first.

| Removed | Use instead |
|---|---|
| `loginWithBrowser()`, `ConsoleBrowserLoginOptions` | `loginWithDevice()`, which stores the login the CLI shares. See [Console authentication](https://github.com/vendurehq/vendure/blob/major/packages/cli/CONSOLE_AUTH.md). |
| `refreshSession()`, `ConsoleRefreshOptions`, `ConsoleTokenGrantError` | `getAccessToken()`, which renews the stored login, or `refreshAccessToken()` after a 401 |
| Imports from `@vendure/cli/dist/commands/console/cli-auth` | The package root, `@vendure/cli` |
| `ConsoleSession.refreshToken` | Nothing. The session an `afterConsoleLink` hook gets never carried one. |

## vendure dev

`vendure dev` is declared with `defineCommand`, like the CLI's other agent-ready commands.

| Before | In v4 |
|---|---|
| `vendure dev --project <dir>` | `vendure dev --dir <dir>`. `--project` names the Vendure Cloud project. |
| Ctrl+C ended the run with exit code 130 | A run stopped with Ctrl+C or SIGTERM ends with exit code 0. A run that a process ends with an error exits 1. |
| `devCommand()`, imported from `@vendure/cli/dist/commands/dev/dev.js` | Run `vendure dev`. Files under `dist` are not a public API of `@vendure/cli`. |
| A CLI plugin could add options to `dev` and wrap its action with `extendCommands` | That extension is skipped, with a warning, and the plugin's other commands still load. Declare an `extensions` entry with `defineCommandExtension` instead, which adds typed fields and wraps `run` with `next()` (see [Extending a command](/guides/developer-guide/cli/#extending-a-command)). A plugin can still replace `dev` with `replaces: true`. |

Update scripts, `package.json` scripts and CI jobs that pass `--project` to `vendure dev`.

## vendure console

`vendure console link`, `status` and `unlink` are declared with `defineCommand`, like the CLI's other agent-ready
commands. They are also tools of the Developer MCP.

| Before | In v4 |
|---|---|
| `vendure console link --project <dir>` | `vendure console link --dir <dir>`. The same applies to `status` and `unlink`. |
| `vendure console link --console-project <id\|slug>` | `vendure console link --project <id\|slug>`. A `--project` value that is a Vendure project directory is refused with the coded error `console.project-is-directory`. |
| `--force` replaced a link with another Console Project, or removed a link, without asking | Each needs a named consent: `replaceLink` for `link`, and `removeLink` for `unlink`. A person at a terminal is asked. Without one, the command returns `incomplete` with a `consent` need, and you run it again with `--replace-link <digest>` or `--remove-link <digest>`. |
| `vendure console link --force` without `--console-project` chose a new Project in the terminal | Run `vendure console unlink`, then `vendure console link`. |
| `--yes` answered the CLI's confirmations, including replacing and removing a link | `--yes` is gone from `vendure console`. It never gives a consent. Without a person at a terminal, a repair runs plugin setup without asking, as before. |
| `--json` wrote a `ConsoleCommandResult` (`schemaVersion`, `operation`, `outcome`, `data`, `needs`, `nextSteps`) | `--json` writes the envelope that every command writes. `link` returns `outcome`, `manifestPath`, `project`, `account`, `plugins` and `nextSteps` as its output, its needs as an `incomplete` result, a plugin setup that failed after the link as a `failed` result with that output, and a link that failed as the coded error `console.link-failed`. `ConsoleCommandResult` is deprecated. |
| `--non-interactive` | Removed. A run never prompts without a person at a terminal: under `--json`, through the Developer MCP, with `CI` or `VENDURE_CLI_NON_INTERACTIVE` set, or without a TTY. |
| A CLI plugin could add options to `console` and wrap its action with `extendCommands` | That extension is skipped, with a warning. Declare an `extensions` entry with `defineCommandExtension` instead (see [Extending a command](/guides/developer-guide/cli/#extending-a-command)). `afterConsoleLink` hooks run as before. |
| An `afterConsoleLink` hook read the parsed options in `context.options`: `project` (the directory), `consoleProject`, `organization`, `force`, `yes`, `json`, `nonInteractive` and plugin flags | `context.options` holds the command's input: `dir` (the directory, which was `project`), `consoleProject` (unchanged) and `organization`. Hooks no longer get `project`. `json`, `nonInteractive`, `yes`, `force` and plugin flags are gone. Read `context.force` for the `replaceLink` consent, and `context.outputMode` and `context.isNonInteractive` for the rest. |
| An `afterConsoleLink` hook's `needs` went into the `--json` result as they were | Without a person, a need with a `fix`, or an `input` need for `dir`, `project` or `organization`, makes the result `incomplete`. Any other need is reported as a next step, and the result is `failed`. |

Update scripts and CI jobs that pass `--project <dir>`, `--console-project`, `--force`, `--yes` or `--non-interactive`
to `vendure console`.

Without a person at a terminal, as in CI, scripts and agents, an error that an `afterConsoleLink` hook throws is
reported in general terms: `The <plugin> plugin failed after linking: Setup did not finish.` This is deliberate, because
CI logs can be public and a hook's error can hold anything the plugin put in it. To see the hook's own message, run
`vendure console link` at a terminal, or read the hook's own logs. Errors the CLI writes itself are always reported as
they are.

### GraphQL API

| Removed | Use instead |
|---|---|
| `SearchInput.facetValueIds` and `SearchInput.facetValueOperator` (Shop and Admin API) | `SearchInput.facetValueFilters`. `facetValueIds: [a, b]` with `AND` becomes `[{ and: a }, { and: b }]`; with `OR` it becomes `[{ or: [a, b] }]`. |
| `Channel.currencyCode` (Shop and Admin API) | `Channel.defaultCurrencyCode` |
| `currencyCode` on `CreateChannelInput` and `UpdateChannelInput` | `defaultCurrencyCode`. It is now required on `CreateChannelInput`. |
| `Fulfillment.summary` (Shop and Admin API) | `Fulfillment.lines` |
| `RefundOrderInput.shipping` and `RefundOrderInput.adjustment` | `RefundOrderInput.amount`, or `targets` to split a refund over several Payments |

`refundOrder` no longer works out the amount from `lines`, `shipping` and `adjustment`. Give the amount with `amount` or `targets`; without either, it returns a `NothingToRefundError`. `lines` is still accepted and records which OrderLines the refund relates to. An `amount` must fit within the selected Payment: to refund more than one Payment holds, use `targets`. Before v4 a line-based refund was split over the Order's Payments automatically.

`Refund.items`, `Refund.shipping` and `Refund.adjustment` are kept for Refunds created before v4.0, and are 0 for Refunds created since. In `modifyOrder`, a refund without an `amount` still refunds the whole difference in the order total, and still draws on the Order's other Payments if the selected one does not cover it.
