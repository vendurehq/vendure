This guide provides guidance for updating the Vendure Framework to a newer version.

## How to update

First, check the [changelog](https://github.com/vendurehq/vendure/blob/master/CHANGELOG.md) for an overview of the changes and any breaking changes in the next version.

In your project's `package.json` file, find all the `@vendure/...` packages and change the version
to the latest. All the Vendure packages have the same version, and are all released together.

```diff
{
  // ...
  "dependencies": {
-    "@vendure/common": "1.1.5",
+    "@vendure/common": "1.2.0",
-    "@vendure/core": "1.1.5",
+    "@vendure/core": "1.2.0",
     // etc.
  }
}
```

Then run `npm install` or `yarn install` depending on which package manager you prefer.

## Upgrading to v4: Node.js and build tooling

Vendure v4 raises the minimum Node.js version, compiles TypeScript with TypeScript 7, and moves the Dashboard's build tooling to Vite 8, which bundles with [Rolldown](https://rolldown.rs/). Apart from updating the `@vendure/...` packages, make the following changes to your project.

### Node.js 22.12 or newer

Vendure v4 requires Node.js `>=22.12.0`. Node.js v20 reached end-of-life on 30 April 2026 and is no longer supported.

### Vite 8

`@vendure/dashboard` declares `vite` as a peer dependency (`^8.0.0`), so your project's own `vite` dependency drives the Dashboard build. Projects created with `@vendure/create` before v4 list `vite` at `^7`. Update it:

```diff
{
  "devDependencies": {
-    "vite": "^7.3.1",
+    "vite": "^8.3.5",
  }
}
```

If your `vite.config.mts` uses `__dirname`, use `import.meta.dirname` instead. Vite 8 warns about `__dirname`, because its planned native config loader does not support it:

```diff title="vite.config.mts"
 export default defineConfig({
     build: {
-        outDir: join(__dirname, 'dist/dashboard'),
+        outDir: join(import.meta.dirname, 'dist/dashboard'),
     },
     // ...
 });
```

If your Vite config adds `@vitejs/plugin-react` itself, update it to v6. Version 6 no longer accepts a `babel` option; Babel plugins go through [`@rolldown/plugin-babel`](https://www.npmjs.com/package/@rolldown/plugin-babel) instead. Options under `build.rollupOptions` are now `build.rolldownOptions`.

The Dashboard compiles Lingui macros (in its own source and in your Dashboard extensions) with Babel. In v3 a file that Babel failed to compile was logged and skipped. In v4 the error fails the build, with the file and location of the problem.

### Testing with Vitest

If you test your plugins with Vitest, update to Vitest 4, which is the first version that supports Vite 8. See the [Vitest 4 migration guide](https://vitest.dev/guide/migration) for its other changes.

If you use `unplugin-swc` to compile decorators in your tests, update it to v2:

```bash
npm install --save-dev vitest@^4 unplugin-swc@^2
```

Older `unplugin-swc` versions only turn off esbuild, which Vite 8 no longer uses. Vite's own Oxc transform then compiles your TypeScript before SWC does, so SWC options such as `useDefineForClassFields: false` are no longer reliably applied. See the [Testing guide](/developer-guide/testing/) for a complete configuration.

### TypeScript 7

Vendure v4 recommends TypeScript 7, the native TypeScript compiler, which compiles projects many times faster.
New projects are set up for it automatically. TypeScript 7 is not required, though: projects can stay on
TypeScript 5.x (see [Staying on TypeScript 5.x](#staying-on-typescript-5x)).

`@vendure/cli` and `@vendure/dashboard` bring their own TypeScript 7, which they use internally: to run your
TypeScript files in `vendure dev`, to check tsconfig files, and to compile your Vendure config for the Dashboard.
This adds about 32 MB to your install, unless your project uses the same TypeScript version.

#### Moving to TypeScript 7

1. Update the `typescript` dev dependency to `"7.1.0-beta || ~7.1.0"`. This is the range that `@vendure/cli` and
   `@vendure/dashboard` use, so your project only installs one copy of TypeScript.
2. Update your `tsconfig.json` files. TypeScript 7 no longer accepts some options that v3 projects commonly use,
   and changes some defaults:
   - **Remove `baseUrl`.** Entries in `paths` are now resolved relative to the tsconfig file that declares them, so
     `"@plugins/*": ["./src/plugins/*"]` keeps working without it.
   - **Set `rootDir`** whenever `outDir` is set and your source files are in a subdirectory, e.g.
     `"rootDir": "./src"`. Without it, TypeScript 7 fails with error TS5011.
   - **Replace `"moduleResolution": "node"`** with `"nodenext"` (and `"module": "nodenext"`) or `"bundler"`.
   - **List the `@types` packages you rely on in `types`.** The `types` option now defaults to `[]`, so `@types`
     packages are no longer included automatically. Without `"types": ["node"]`, Node.js globals such as `process` and
     `Buffer` are errors (TS2591).
   - **Keep `useDefineForClassFields` disabled.** If your tsconfig sets a `target` of ES2022 or later, or no
     `target` at all (TypeScript 7 defaults to a newer target), add `"useDefineForClassFields": false`. Otherwise
     fields declared on your entity classes are reset after the constructor runs, so e.g.
     `new Product({ name: 'Laptop' })` loses its input.
   - **Remove the `"ts-node"` section.** It is ignored, because ts-node is no longer used (see below).

   ```diff title="tsconfig.json"
   {
     "compilerOptions": {
       "module": "nodenext",
       "moduleResolution": "nodenext",
       "outDir": "./dist",
   +   "rootDir": "./src",
   +   "types": ["node"],
   +   "useDefineForClassFields": false,
   -   "baseUrl": "./",
       // ...
     },
   -  "ts-node": {
   -    "files": true
   -  }
   }
   ```

   Run `npx vendure doctor --check typescript` to list any remaining problems. `vendure build` also checks your
   tsconfig files before compiling.

3. **If you use npm**, add `@nestjs/graphql` as a dependency, with the same range as `@vendure/core`, and override
   its TypeScript peer dependency. `@nestjs/graphql` declares an optional peer dependency on TypeScript 5 or 6, so
   with TypeScript 7 in your project npm installs it under `node_modules/@vendure/core/node_modules`, where the
   Dashboard plugin and your own GraphQL resolvers can no longer import it (`Cannot find module '@nestjs/graphql'`).
   The override keeps the TypeScript versions that `@nestjs/graphql` accepts and adds TypeScript 7, so it also
   works in workspaces where another package (such as a storefront) uses TypeScript 6. `@nestjs/graphql` only uses
   TypeScript for its optional compiler plugin.
   New projects created with npm include this. pnpm, Yarn and Bun are not affected.

   ```diff title="package.json"
   {
     "dependencies": {
   +   "@nestjs/graphql": "~14.0.0",
       // ...
     },
   + "overrides": {
   +   "@nestjs/graphql": {
   +     "typescript": "^5.5.0 || ^6.0.0 || 7.1.0-beta || ~7.1.0"
   +   }
   + }
   }
   ```

#### Changes for all projects

1. **The Vendure CLI no longer uses ts-node**, which cannot run on TypeScript 7.
   `vendure dev`, `vendure migrate` and the other CLI commands now run your TypeScript files with a require hook
   provided by `@vendure/cli`, which keeps decorator metadata (used by Vendure's dependency injection and entities)
   and registers the `paths` from your tsconfig automatically, so you no longer need `tsconfig-paths/register`.
   It works with TypeScript 5.x tsconfig files too. To run your own TypeScript scripts, replace `ts-node` with
   `node --require @vendure/cli/register`, and remove ts-node from your dependencies (projects on TypeScript 5.x
   can keep using ts-node for their own scripts):

   ```diff title="package.json"
   {
     "scripts": {
   -   "migration:generate": "ts-node migration.ts generate",
   +   "migration:generate": "node --require @vendure/cli/register migration.ts generate",
   -   "my-script": "ts-node -r tsconfig-paths/register ./src/my-script.ts"
   +   "my-script": "node --require @vendure/cli/register ./src/my-script.ts"
     }
   }
   ```

   The hook uses the nearest `tsconfig.json` to the current working directory. Set the `VENDURE_TSCONFIG`
   environment variable to use a different one.
2. **`vendure dev` no longer type-checks your code.** In v3 it ran your server with ts-node, which reported type
   errors when the server started. The new hook compiles each file without type checking, like ts-node's
   `transpileOnly` mode, so a type error no longer stops the server. Check types with your editor, with
   `npx tsc --noEmit --watch` in a separate terminal, or with `vendure build`, which type-checks before emitting.
3. The `--experimental-tsgo` option of `vendure build` is deprecated and has no effect. `vendure build` runs your
   project's own `tsc`, which is the native compiler from TypeScript 7 onwards.

#### Staying on TypeScript 5.x

If your project can't move to TypeScript 7 yet, for example because it shares its TypeScript version with the
rest of a monorepo, keep its `typescript` dependency and tsconfig files as they are. Vendure's type declarations
are built with TypeScript 7 and work with TypeScript 5.4 and later.

`vendure build` runs your project's own `tsc`. The TypeScript 7 tsconfig checks described above only run when that
is TypeScript 7 or later. Otherwise the build logs that it skips them. The `useDefineForClassFields` advice above
still applies if your tsconfig sets a `target` of ES2022 or later.

A project on TypeScript 5.x gives up:

- **Build speed.** TypeScript 7 compiles about 9 times faster (measured on `@vendure/core`: 4.9s with TypeScript
  5.8, 0.5s with TypeScript 7).
- **One TypeScript install.** Your project installs both its own TypeScript 5.x and the TypeScript 7 that
  `@vendure/cli` and `@vendure/dashboard` use internally.
- **Early warning about TypeScript 7.** `vendure doctor` warns that TypeScript 7 is recommended, and lists the
  tsconfig changes that it needs, but `vendure build` does not check for them.

`vendure dev` and the other CLI commands compile your TypeScript files with the CLI's own TypeScript 7, using the
options from your tsconfig. They work with TypeScript 5.x tsconfig files, including `baseUrl` and
`"moduleResolution": "node"`.

## Versioning Policy & Breaking changes

Vendure generally follows the [SemVer convention](https://semver.org/) for version numbering. This means that breaking API changes will only be introduced with changes to the major version (the first of the 3 digits in the version).

However, there are some exceptions to this rule:

- In minor versions, (e.g. v2.0 to v2.1) we may update underlying dependencies to new major versions, which may in turn introduce breaking changes. These will be clearly noted in the changelog.
- In minor versions we may also occasionally introduce non-destructive changes to the database schema. For instance, we may add a new column which would then require a database migration. We will _not_ introduce database schema changes that could potentially result in data loss in a minor version.

Any instances of these exceptions will be clearly indicated in the [Changelog](https://github.com/vendurehq/vendure/blob/master/CHANGELOG.md). The reasoning for these exceptions is discussed in the [Versioning policy RFC](https://github.com/vendurehq/vendure/issues/1846).

### What kinds of breaking changes can be expected?

Major version upgrades (e.g. v1.x to v2.x) can include:

* Changes to the database schema
* Changes to the GraphQL schema
* Updates of major underlying libraries, such as upgrading NestJS to a new major version

Every release will be accompanied by an entry in the [changelog](https://github.com/vendurehq/vendure/blob/master/CHANGELOG.md), listing the changes in that release. And breaking changes are clearly listed under a **BREAKING CHANGE** heading.

### Database migrations

Database changes are one of the most common causes for breaking changes. In most cases, the changes are minor (such as the addition of a new column) and non-destructive (i.e. performing the migration has no risk of data loss).

However, some more fundamental changes occasionally require a careful approach to database migration in order to preserve existing data.

The key rule is **never run your production instance with the `synchronize` option set to `true`**. Doing so can cause inadvertent data loss in rare cases.

For any database schema changes, it is advised to:

1. Read the changelog breaking changes entries to see what changes to expect
2. **Important:** Make a backup of your database!
3. Create a new database migration as described in the [Migrations guide](/developer-guide/migrations/)
4. Manually check the migration script. In some cases manual action is needed to customize the script in order to correctly migrate your existing data.
5. Test the migration script against non-production data.
6. Only when you have verified that the migration works as expected, run it against your production database.

### GraphQL schema changes

If you are using a code-generation tool (such as [graphql-code-generator](https://graphql-code-generator.com/)) for your custom plugins or storefront, it is a good idea to re-generate after upgrading, which will catch any errors caused by changes to the GraphQL schema.

### TypeScript API changes

If you are using Vendure providers (services, JobQueue, EventBus etc.) in your custom plugins, you should look out for breakages caused by changes to those services. Major changes will be listed in the changelog, but occasionally internal changes may also impact your code. 

The best way to check whether this is the case is to build your entire project after upgrading, to see if any new TypeScript compiler errors emerge.
