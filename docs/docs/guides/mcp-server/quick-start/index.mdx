The MCP plugin exposes your Vendure store to AI agents over the [Model Context Protocol](https://modelcontextprotocol.io/)
(MCP) — an open standard that lets agents such as Claude, Cursor and ChatGPT discover and call tools on a server.
The plugin ships 42 built-in tools (browsing the catalog, managing a cart, placing an order, and admin operations
like creating products or refunding orders), and any Vendure plugin can add its own with the
[`@McpTool`](/reference/core-plugins/mcp-plugin/mcp-tool/) decorator.

This guide gets a server running, connects a client, and shows you how to debug. For the OAuth handshake that
authenticates agents, see the [OAuth & Consent](/guides/mcp-server/oauth-consent/) guide.

## Install

Add the plugin to your Vendure config. The full option surface is documented on
[`McpPluginOptions`](/reference/core-plugins/mcp-plugin/mcp-plugin-options/); the essentials are below.

```ts title="src/vendure-config.ts"
import { McpPlugin } from '@vendure/mcp-plugin';

export const config: VendureConfig = {
    // ...
    plugins: [
        McpPlugin.init({
            oauth: {
                // Server secret used to HMAC-hash OAuth tokens at rest.
                // Generate once with: openssl rand -base64 32
                tokenSecret: process.env.MCP_TOKEN_SECRET,
                // Public base URL of this server. Used as the OAuth issuer and to
                // build the metadata URLs agents discover.
                issuer: 'https://my-store.example.com',
                // The storefront page that approves customer (shop) consent. Only needed
                // if customers will authorize MCP clients.
                storefrontConsentUrl: 'https://my-storefront.example.com/mcp/authorize',
            },
        }),
    ],
};
```

The `oauth` block is optional. Omit it and the OAuth surface is disabled — the anonymous shop endpoint still works,
but the authenticated shop and admin endpoints do not. See [`McpOauthOptions`](/reference/core-plugins/mcp-plugin/mcp-oauth-options/)
for every field and its default.

:::info
When `NODE_ENV=production` the plugin refuses to boot with the default `http://localhost:3500` issuer — set it to
your real public URL. `storefrontConsentUrl` has no default and is needed only if customers will authorize MCP
clients; when you do set it, it must be a public HTTPS URL. This is covered in the
[Production & Observability](/guides/mcp-server/production/) guide.
:::

### Database migration

Enabling `McpPlugin` registers **5 new entities**:

- `McpOauthClient`
- `McpAuthorizationCode`
- `McpAuthorizationRequest`
- `McpOauthGrant`
- `McpToolCallLog`

If you run with `synchronize: false` (the recommended production setting), generate and run a migration so these
tables are created. See [Migrations](/guides/developer-guide/migrations/) for the workflow.

## The two endpoints

The plugin serves MCP over Streamable HTTP at two paths:

| Endpoint | Access | Purpose |
|---|---|---|
| `POST /mcp/shop` | Anonymous, or a customer Bearer token | Shop tools — browse the catalog, manage a cart, place an order |
| `POST /mcp/admin` | Administrator Bearer token (required) | Admin tools — manage products, orders, customers, stock |

Both endpoints expect `Content-Type: application/json` and an
`Accept: application/json, text/event-stream` header (the MCP SDK client sets these for you). A `GET` to either
path returns `405 Method Not Allowed` with an `Allow: POST` header — MCP is POST-only here (there is no
server-initiated SSE stream). An unauthenticated call to `/mcp/admin` returns `401` with a
`WWW-Authenticate: Bearer` header pointing at the protected-resource metadata, which is how an MCP client
discovers where to start the OAuth flow.

## Connect a client

MCP clients that support remote (Streamable HTTP) servers connect by URL. The shop endpoint can be used
anonymously; the admin endpoint (and the authenticated shop endpoint) trigger the OAuth flow, which the client
runs for you.

```json title="Example MCP client configuration"
{
    "mcpServers": {
        "vendure-shop": {
            "url": "https://my-store.example.com/mcp/shop"
        }
    }
}
```

:::tip
The dashboard **MCP Server** overview page (under the *System* menu) shows ready-to-copy connection snippets for
both endpoints. See the [OAuth & Consent](/guides/mcp-server/oauth-consent/) guide for how admin sign-in works
through the dashboard.
:::

## Test & debug with the MCP Inspector

The [MCP Inspector](https://github.com/modelcontextprotocol/inspector) is a browser-based tool for exploring a
server — the MCP equivalent of GraphiQL. Run it with no install:

```sh
npx @modelcontextprotocol/inspector
```

Point it at `https://my-store.example.com/mcp/shop` to browse and call shop tools anonymously, or at
`/mcp/admin` with a Bearer token to exercise the admin tools. It lists the live tool set, shows each tool's input
schema, and lets you run calls and inspect the results — the fastest way to see what an agent will see.

## Direct vs discovery tool exposure

By default the server lists every permitted tool directly (`toolExposure: 'direct'`). This is the right choice for
almost all deployments: modern agents and hosts have their own tool-search, and listing tools normally lets that
work.

If you connect a host with a low tool cap or a model without built-in tool search, you can opt into
`toolExposure: 'discovery'`, which replaces the full list with two meta-tools (`search_tools` and `execute_tool`).
The [Built-in Tool Reference](/guides/mcp-server/built-in-tools/#tool-exposure-direct-vs-discovery) explains when to
reach for it.
