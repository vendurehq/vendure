Any Vendure plugin can add its own MCP tools. You write a normal injectable service class, decorate it with
[`@McpTool`](/reference/core-plugins/mcp-plugin/mcp-tool/), and register it as a provider. The MCP plugin's
registry discovers it at bootstrap, compiles its schema, and exposes it on the shop or admin endpoint alongside
the built-in tools.

## The contract package

The tool-authoring contract — the `@McpTool` decorator and its types — lives in its own tiny package,
**`@vendure/mcp-sdk`**. Author tools against that package, not `@vendure/core` and not `@vendure/mcp-plugin`:

```sh
npm install @vendure/mcp-sdk
```

`@vendure/mcp-sdk` is inert: it has no runtime dependencies — Standard Schema support is a structural TypeScript
interface, not a dependency on any schema library. It exists so a plugin can *declare* tools without pulling in
the whole server. The server (`@vendure/mcp-plugin`) must be installed and `McpPlugin` added to your config for
the tools to actually be served.

:::warning Keep a single copy of `@vendure/mcp-sdk`
The `@McpTool` decorator is created with NestJS's `DiscoveryService.createDecorator()`, which creates its metadata
key once, at module load. If two different versions of `@vendure/mcp-sdk` resolve in your `node_modules`, they
create two different keys, and tools decorated via one copy are **invisible** to a registry scanning with the other
— they silently never appear. Vendure's fixed versioning and your package manager's deduplication normally
prevent this; the rule for plugin authors is simply: **do not pin a divergent `@vendure/mcp-sdk` version**.
:::

## A minimal tool

A tool is an `@Injectable()` class with the `@McpTool` decorator and an `execute(ctx, input)` method. Implement
[`McpToolHandler`](/reference/core-plugins/mcp-plugin/mcp-tool-handler/) from `@vendure/mcp-sdk` for type-safety:

```ts title="src/tools/low-stock.tool.ts"
import { Injectable } from '@nestjs/common';
import { Permission, ProductVariantService, RequestContext } from '@vendure/core';
import { McpTool, McpToolHandler } from '@vendure/mcp-sdk';

interface LowStockInput {
    threshold: number;
}

@McpTool({
    name: 'find_low_stock_variants',
    toolset: 'admin',
    description: 'List product variants whose stock on hand is at or below a threshold.',
    permissions: [Permission.ReadCatalog],
    behavior: 'readonly',
    inputSchema: {
        type: 'object',
        properties: {
            threshold: { type: 'number', description: 'Stock-on-hand level to report at or below.' },
        },
        required: ['threshold'],
        additionalProperties: false,
    },
})
@Injectable()
export class FindLowStockVariantsTool implements McpToolHandler<LowStockInput> {
    constructor(private productVariantService: ProductVariantService) {}

    async execute(ctx: RequestContext, input: LowStockInput) {
        // ...query variants, return a plain serializable summary
        return { variants: [] };
    }
}
```

Register the class as a provider in the plugin that owns it:

```ts title="src/my-plugin.ts"
@VendurePlugin({
    imports: [PluginCommonModule],
    providers: [FindLowStockVariantsTool],
})
export class MyPlugin {}
```

That is all — the MCP registry discovers every `@McpTool` provider across the running app at bootstrap.

## Tool names share one namespace

Within a toolset, every tool name — yours and Vendure's built-in ones — lives in a single flat namespace, and a
duplicate name is a startup error naming both sources. That is the right behaviour for a genuine clash, but it
has a forward-compatibility consequence: if a later Vendure release ships a built-in tool with the same name as
yours, servers running your plugin will refuse to start after the upgrade. Prefix your tool names with something
specific to your plugin — `wishlist_add_item` rather than `add_item` — so a future built-in name cannot collide
with yours.

## Input and output schemas

`inputSchema` and `outputSchema` accept two forms:

1. **A plain JSON Schema object** ([`McpJsonSchema`](/reference/core-plugins/mcp-plugin/mcp-json-schema/)) — the MCP wire format itself, written by hand.
2. **A Standard Schema object** ([`McpStandardSchema`](/reference/core-plugins/mcp-plugin/mcp-standard-schema/)) — a schema from any library implementing the [Standard Schema](https://standardschema.dev/) interface with JSON Schema conversion. Zod v4, ArkType, and Valibot all qualify. The server converts it to JSON Schema once at startup to advertise the tool, and uses the library itself to validate every call.

With a Standard Schema you define the shape once and derive the TypeScript type from it:

```ts
import { z } from 'zod';

const lowStockInput = z.object({
    threshold: z.number().int().min(0).describe('Stock-on-hand level to report at or below.'),
});

@McpTool({
    name: 'find_low_stock_variants',
    toolset: 'admin',
    description: 'List product variants whose stock on hand is at or below a threshold.',
    permissions: [Permission.ReadCatalog],
    behavior: 'readonly',
    inputSchema: lowStockInput,
})
@Injectable()
export class FindLowStockVariantsTool implements McpToolHandler<z.infer<typeof lowStockInput>> {
    async execute(ctx: RequestContext, input: z.infer<typeof lowStockInput>) {
        // input is fully typed — and it is the library-parsed value, so defaults
        // and coercions have already been applied.
    }
}
```

There is no per-request validation to wire up in either form: the server validates every call's
arguments before your `execute` runs. Anything that is neither form — including a Zod v3 schema,
which cannot emit JSON Schema — is a TypeScript error at the decorator, and if it reaches the
registry it aborts startup with an error naming the offending tool.

:::caution Standard Schema needs Zod v4.2+
If your project resolves Zod **v3** (still common as a transitive dependency), a Zod schema
satisfies *neither* accepted form, and TypeScript's error is misleading: it complains the schema
is not assignable to `McpJsonSchema` and is missing a `type` property, without mentioning Zod
versions at all. If you hit that error on a Zod schema, check what actually resolved
(`npm ls zod`) — you need Zod **4.2 or later** for the JSON Schema conversion, or author the
schema as a plain JSON Schema object, which works regardless of Zod version.
:::

- Omitting `inputSchema` means the tool accepts **no** arguments (the server publishes
  `{ type: 'object', properties: {}, additionalProperties: false }`), not "accepts anything".
- Hand-written JSON Schemas should declare `additionalProperties: false` so unknown fields are
  rejected. Zod strips unknown keys by default; use `z.strictObject()` to reject them instead.
- `outputSchema` is a diagnostic: the server logs a warning when a tool's output drifts from it,
  but never fails the call.

## Permissions use OR semantics

`permissions` is a list of [`Permission`](/reference/typescript-api/common/permission/) values, evaluated with
**OR**: the caller needs *any one* of them. Use `Permission.Public` for anonymous shop tools and
`Permission.Authenticated` for tools that only need a signed-in user. When you list fine-grained permissions,
match the permissions the equivalent Admin GraphQL operation requires, so a tool is never more permissive than
the API it wraps.

Omitting `permissions` means different things on each toolset. On a `shop` tool, omitted (or an empty array) means
`Permission.Public` — callable by anyone who can reach the shop endpoint. On an `admin` tool, `permissions` is
required: the registry aborts boot, naming the tool, if it is missing or empty. If any administrator may call it,
say so with `[Permission.Authenticated]` — an explicit `[Permission.Public]` is also accepted, but reads as
"anonymous allowed" on an admin tool, which is misleading since both behave the same on the admin endpoint.

## Destructive tools and confirmation

Mark a tool that deletes, cancels, refunds, or otherwise makes a hard-to-reverse change with
`behavior: 'destructive'`. The registry then does the confirmation handshake for you:

- It advertises an optional `confirm: boolean` parameter on the tool's schema.
- On a call without `confirm: true`, it returns a non-error response describing the action and asking the agent
  to re-call with confirmation — your `execute` is not run.
- On `confirm: true`, it strips `confirm` and runs your `execute`.

**You never add `confirm` to your `inputSchema` or read it in `execute` — the registry owns it.** In fact, a
destructive tool that declares its own `confirm` property fails at bootstrap, to stop the two mechanisms
colliding.

This holds for both schema forms: for a Standard Schema tool the registry validates your fields
with your schema and handles `confirm` itself, so even a strict Zod schema never sees it. One
constraint: a destructive tool's schema must parse to a plain object — a schema whose output is
transformed to a string or array is rejected at call time.

```ts title="src/tools/archive-product.tool.ts"
@McpTool({
    name: 'archive_product',
    toolset: 'admin',
    description: 'Permanently archive a product so it can no longer be sold.',
    permissions: [Permission.DeleteCatalog],
    behavior: 'destructive', // the registry gates confirmation
    inputSchema: {
        type: 'object',
        properties: { id: { type: 'string', description: 'Product ID to archive.' } },
        required: ['id'],
        additionalProperties: false,
        // Note: no `confirm` here — the registry adds and gates it.
    },
})
@Injectable()
export class ArchiveProductTool implements McpToolHandler<{ id: string }> {
    // ...
}
```

See [How tool safety is derived](/guides/mcp-server/built-in-tools/#how-tool-safety-is-derived) for what each
`behavior` value means.

## Discovery keywords

The optional `keywords` field is **author-time, search-only metadata**. In discovery mode the server ranks tools
against a user's `search_tools` query, and your keywords join the tool's name, title, and description in the
searchable text. Use them for the synonyms and phrasings a user would actually say that don't appear in the
description:

```ts
keywords: ['money back', 'reimburse', 'return payment'],
```

Keywords are **never serialized** into a tool listing or sent to the agent — they only tune search. They have no
effect in the default `direct` exposure mode. See
[Tool exposure](/guides/mcp-server/built-in-tools/#tool-exposure-direct-vs-discovery) for how discovery works.

## Metadata reference

The full field list, types, and defaults are on
[`McpToolMetadata`](/reference/core-plugins/mcp-plugin/mcp-tool-metadata/). In brief:

| Field | Purpose |
|---|---|
| `name` | Unique snake_case tool name |
| `title` | Optional human-friendly title |
| `description` | Agent-facing description — write it for the model |
| `toolset` | `'shop'` or `'admin'` — which endpoint serves it |
| `permissions` | `Permission[]`, OR semantics. Omitted/empty on `shop` defaults to Public; required on `admin` — boot fails without it |
| `behavior` | Safety classification: `'readonly'`, `'mutating'` (default), or `'destructive'` |
| `inputSchema` / `outputSchema` | JSON Schema or Standard Schema (e.g. Zod v4); input validated pre-call, output drift-checked post-call |
| `keywords` | Search-only synonyms for discovery mode |

## Accessing who is calling

`execute(ctx, input)` is enough for almost every tool. If you need to know who is calling — the OAuth grant behind
the call, or the client IP — `execute` takes an optional third argument,
[`McpCallerInfo`](/reference/core-plugins/mcp-plugin/mcp-caller-info/), from `@vendure/mcp-sdk`:

```ts
import { McpCallerInfo, McpToolHandler } from '@vendure/mcp-sdk';

export class MyTool implements McpToolHandler<MyInput> {
    async execute(ctx: RequestContext, input: MyInput, caller?: McpCallerInfo) {
        const grant = caller?.grant; // the OAuth grant info, when present
        // ...
    }
}
```

`caller` is absent for anonymous shop calls and for in-process calls made via `McpToolExecutionService`. A tool
never needs to depend on `@vendure/mcp-plugin` — everything a tool implements comes from `@vendure/mcp-sdk`.
