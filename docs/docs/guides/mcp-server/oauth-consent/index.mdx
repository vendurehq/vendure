MCP clients authenticate to the Vendure server using **OAuth 2.1** with PKCE. A client identifies itself either
with a **Client ID Metadata Document** (CIMD — its `client_id` is an HTTPS URL the server fetches its details
from) or, as the older fallback, by registering itself via Dynamic Client Registration. The client runs almost
the entire flow for you — it discovers the endpoints, identifies itself, and exchanges tokens. The one part that
needs a decision from a person is **consent**: somebody has to agree that this client may act on their behalf.

Who that person is, and whether they ever see a screen, depends on what you are building. Sort yourself first.

## Which of these are you doing?

**Staff tools only** — your team queries the store with an AI client such as Claude Desktop or Cursor.
You need [Admin consent](#admin-consent-ships-with-the-dashboard) below. Vendure ships that page, so there is
nothing for you to build. Nothing else here applies to you.

**A chat assistant you build as a Vendure plugin.** No browser, no consent page, no popup, no token — it runs the
tools directly. See [Assistant inside Vendure](/guides/mcp-server/assistant-inside-vendure/).

**A chat assistant you run outside Vendure**, as a separate service with its own front end. You need the full
OAuth round trip, but the shopper never notices it if you run it during a page navigation they were making
anyway. See [Assistant outside Vendure](/guides/mcp-server/assistant-outside-vendure/).

**Shoppers bringing their own AI client** — Claude Desktop, ChatGPT, Cursor — and pointing it at your store.
Each shopper approves once, on a page you host. That is
[the customer consent page](#the-customer-consent-page) below, and it is the same page the previous case needs.

## What ships with the plugin, and what you build

- **Admin consent works out of the box.** The plugin ships a consent page inside the dashboard. An administrator
  holding the `UpdateMcpServer` permission approves a client using their existing dashboard session — no extra
  build, no separate login.
- **Customer consent needs a page you host**, and only if customers will authorize clients at all. Your
  storefront owns customer login, so the plugin cannot render that screen for you. Build one page against
  [the customer consent page](#the-customer-consent-page) contract below. If nothing but the admin toolset is
  ever used, you do not need the page and you do not need to configure its URL.
- **An assistant you build as a Vendure plugin needs neither.** It runs inside the server process, so it calls
  the tools directly instead of sending anyone through a browser. See
  [Assistant inside Vendure](/guides/mcp-server/assistant-inside-vendure/).
- **The richer MCP management dashboard is a fast-follow.** v1 ships an enriched consent page plus a single
  Overview. Multi-page management, a config panel, and OAuth-client inventory are deferred; until then, use the
  Admin GraphQL API and the [MCP Inspector](/guides/mcp-server/quick-start/#test--debug-with-the-mcp-inspector).

## The OAuth 2.1 flow

This is the flow a client outside your server runs. The client drives every step; you only configure `oauth`
(see [`McpOauthOptions`](/reference/core-plugins/mcp-plugin/mcp-oauth-options/)) and, for customer access, host
the consent page. An assistant built as a Vendure plugin skips all of it — see
[Assistant inside Vendure](/guides/mcp-server/assistant-inside-vendure/).

1. **Discover.** A call to a protected endpoint returns `401` with a
   `WWW-Authenticate: Bearer resource_metadata="…"` header. The client fetches that protected-resource metadata,
   then the authorization-server metadata, to learn every endpoint URL.
2. **Identify.** Preferred: the client uses an HTTPS URL as its `client_id` (CIMD); the server fetches the JSON
   document at that URL to learn the client's name and `redirect_uris`, and caches it. No registration call is
   made. Fallback: the client `POST`s to `/mcp/oauth/register` with its `client_name` and `redirect_uris` and
   receives a `client_id` (Dynamic Client Registration — deprecated by the MCP spec as of 2026-07-28, but still
   served for compatibility). Clients are public either way (PKCE, no secret).
3. **Authorize.** The client sends the user to `GET /mcp/oauth/authorize` with `response_type=code`, its
   `client_id`, `redirect_uri`, a PKCE `code_challenge` (`S256`), and the `resource` it wants access to. The
   server records a pending request and **redirects to the consent page** carrying only `?request_token=<requestToken>`.
4. **Consent.** A human approves (admin via the dashboard; customer via your storefront page). On approval the
   server issues a short-lived authorization `code` and redirects back to the client's `redirect_uri`.
5. **Token exchange.** The client `POST`s to `/mcp/oauth/token` with `grant_type=authorization_code`, the `code`,
   its `code_verifier`, and the `resource`, and receives an `access_token` + `refresh_token`.
6. **Call tools.** The client sends `Authorization: Bearer <access_token>` on every MCP request.
7. **Refresh.** When the access token expires, the client exchanges the refresh token for a new pair.

### Endpoints

All URLs are built from your configured `issuer`, so the `issuer` **must** be the public base URL the client can
reach.

| Endpoint | Method | Purpose |
|---|---|---|
| `/.well-known/oauth-authorization-server` | GET | Authorization-server metadata (RFC 8414) |
| `/.well-known/oauth-protected-resource/mcp/{shop\|admin}` | GET | Protected-resource metadata (RFC 9728) |
| `/mcp/oauth/register` | POST | Dynamic Client Registration |
| `/mcp/oauth/authorize` | GET | Start the authorization request (redirects to consent) |
| `/mcp/oauth/token` | POST | Authorization-code exchange and refresh-token rotation |
| `/mcp/oauth/revoke` | POST | Revoke a grant (RFC 7009) |
| `/mcp/oauth/authorization-request` | GET | Consent-page lookup of pending-request details |

Consent decisions are not endpoints in this list. Each is an `authorizeMcpClient` mutation: an administrator's
decision on the **Admin API** (used by the dashboard consent page), and a customer's on the **Shop API**, so
your consent page records it the same way it does everything else — see
[the customer consent page](#the-customer-consent-page).

The token endpoint accepts an `application/x-www-form-urlencoded` body as required by OAuth 2.1 (RFC 6749); the
`/register` and `/revoke` endpoints accept form-encoded bodies too. Standard MCP clients send form-encoded token
requests, and they work as-is.

The authorization-server metadata advertises `S256` PKCE, the `authorization_code` and `refresh_token` grants,
`token_endpoint_auth_methods_supported: ["none"]` (public clients), and
`client_id_metadata_document_supported: true` — the flag MCP clients check before sending a URL `client_id`.

A CIMD `client_id` must be an HTTPS URL with a path, no query or fragment, a hostname rather than an IP address,
and at most 512 characters. It must also already be in the form a URL parser produces — a lowercase host, no
default port, no `.`/`..` or backslash path segments — because the server fetches exactly the address given and
compares it against the document character for character. The server fetches the document without following
redirects, refuses hosts that resolve to private or otherwise special-use addresses, caps the document at 5 KB,
and reuses it for one hour before fetching it again. The document must contain a `client_id` exactly equal to the
URL, a `client_name` of at most 255 characters, and `redirect_uris` (each at most 255 characters, on this and
the `/register` path alike); the redirect URI the client uses must be listed there exactly.

To develop against a metadata document served from your own machine, set
`oauth.allowLoopbackCimdDocuments: true`. That permits a `client_id` URL pointing at `localhost`, `127.0.0.1` or
`::1` over plain HTTP. Leave it off anywhere others can reach: with it on, anyone who can reach the authorize
endpoint — no credentials needed — can make the server open a connection to any port on the machine it runs on.
The server refuses to start with it enabled when `NODE_ENV` is `production`.

The authorize endpoint takes no credentials, and resolving a `client_id` URL makes the server fetch it, so a
flood of distinct URLs means a flood of outbound requests. Rate limiting for the OAuth endpoints is not yet in
place; until it is, restrict access to `/mcp/oauth/*` at your proxy if that matters to you.

### Resource → toolset mapping

Every authorization request names a `resource`, and the resource decides which toolset the grant is for:

- `{issuer}/mcp/shop` → the **shop** toolset
- `{issuer}/mcp/admin` → the **admin** toolset

A resource that matches neither (or carries a query string or fragment) is rejected. The token the client
receives is scoped to that one toolset.

### Token lifetimes and rotation

Access tokens are short-lived (default 15 minutes) and refresh tokens long-lived (default 30 days); both are tuned
via [`McpOauthOptions`](/reference/core-plugins/mcp-plugin/mcp-oauth-options/). Refresh is **rotating**: each
refresh issues a new refresh token and invalidates the previous one. Re-using an already-rotated refresh token is
treated as a compromise signal (OAuth 2.1 reuse detection) and **revokes the whole grant**. Revocation is a
soft-revoke — the grant row is kept (with `revokedAt` set) so the audit trail survives, but the token stops
working immediately.

### The Vendure session behind a grant

Exchanging the authorization code creates one internal Vendure session for the grant. It carries an ordinary
random token generated by Vendure, and that token stays server-side — it is never returned to the MCP client,
which only ever holds the OAuth access and refresh tokens.

That session is **stable**. A refresh rotates the OAuth token pair and leaves the session untouched, so anything
the session holds — active order, active channel, custom fields — survives the rotation. The rotation is written
in a single transaction, so a refresh that cannot be completed leaves the client's existing refresh token working
for a retry.

The session's lifetime is Vendure's ordinary sliding expiry, the same as any other session: using it extends it
(Vendure pushes the expiry out once it is more than halfway to expiring). An agent in regular use therefore keeps
its session for as long as it keeps working. Three things end one:

- **Revocation**, which deletes the session row and drops its cache entry in the same operation that marks the
  grant revoked. On a single instance the credential stops working straight away. If you run several instances
  with the default in-memory cache, the other instances keep accepting the cached session for up to 5 minutes
  (`sessionCacheTTL`) — a shared cache fixes this; see the [production guide](/guides/mcp-server/production/).
- **The daily retention task**, which deletes the session of any grant that has passed its own expiry — the case
  where a client simply stopped refreshing for longer than `refreshTokenTtlSeconds`. The task runs once a day
  (03:30 by default, `oauth.retentionSchedule`), so this can lag the grant's expiry by up to a day.
- **Natural expiry**, if a session lapses while its grant is still valid. The next MCP request creates a
  replacement, so a lapsed session never breaks a working grant.

There is no separate maximum age for MCP sessions; they follow the same rules as the rest of your Vendure
sessions. Rotating `oauth.tokenSecret` is the one case that leaves sessions behind for a while: the OAuth tokens
become unresolvable at once, but their grants live until their own expiry, and retention removes the sessions
then — up to `refreshTokenTtlSeconds` (30 days by default) plus a day. Revoking the grants removes their
sessions right away. Nothing about those sessions can be derived from the old access tokens.

## Admin consent (ships with the dashboard)

When an agent requests the **admin** toolset, the authorize step redirects to the dashboard consent page at the
`adminConsentPath` (default `/dashboard/mcp/authorize`). The page reads the pending request, shows the client
name, its redirect URI, and the requested toolset, and lets the signed-in administrator **Approve** or **Deny**.
Approval uses the administrator's existing dashboard session — there is no second login. Under the hood the page
calls the `authorizeMcpClient` mutation on the **Admin API** through the dashboard's own API client, so the
decision is authenticated however the rest of the dashboard is (session cookie or bearer token); the server
checks the session, creates the authorization code, and returns the client redirect URL.

Two things are enforced on that mutation beyond being signed in:

- **The `UpdateMcpServer` permission.** Being an authenticated administrator is not enough — approving is a
  mutation of who can reach your store, so it is gated on the same permission as the other MCP mutations. The
  dashboard route is guarded too, so an administrator holding only `ReadMcpServer` never sees the page; the
  server-side check is what stops the same approval being submitted directly through the API.
- **A same-origin check.** On a cookie-authenticated server the approval rides the administrator's login cookie,
  which the browser attaches automatically, so if the request carries an `Origin` header, it must match the origin
  of your configured `oauth.issuer`, otherwise it is refused. This blocks a third-party page from forging an approval. A request with
  no `Origin` header at all is allowed — that is what lets an API client approve programmatically. A caller
  authenticated by a bearer token gets no exemption from this check: Vendure reads the session cookie before it
  ever looks at `Authorization`, so a page on another site could send a meaningless `Authorization` value and
  still be riding the administrator's own cookie.

The practical consequence of the second rule is that **`oauth.issuer` must be the origin your dashboard is served
from**. If the two differ, the consent page's own submission looks cross-origin and every approval fails. The
same rule also refuses a programmatic approval that happens to send an `Origin` other than that address — send
none at all rather than setting it to something arbitrary.

Nothing to build here — it works as soon as the plugin is installed and the dashboard extension is active.

## The customer consent page

When a client asks for the **shop** toolset, the authorize step redirects the browser to a page you host,
carrying one query parameter: `?request_token=<token>`. That page shows the shopper what is being asked and
records their answer.

### Configuring the page URL

Set `oauth.storefrontConsentUrl` to the absolute URL of that page:

```ts title="src/vendure-config.ts"
McpPlugin.init({
    oauth: {
        tokenSecret: process.env.MCP_TOKEN_SECRET,
        issuer: 'https://my-store.example.com',
        storefrontConsentUrl: 'https://my-storefront.example.com/mcp/authorize',
    },
});
```

There is **no default**. The setting is required only if customers will authorize clients; a store that uses the
admin toolset alone starts up without it. When you do set it, two rules apply once `NODE_ENV=production`: it must
use HTTPS, and it must not be a loopback address such as `localhost` or `127.0.0.1`. The server refuses to boot
otherwise.

If a customer authorization arrives at a server where the setting is missing, the client is sent back to its own
registered redirect address with `error=server_error` and the `state` it supplied, and a short explanation that
the store is not configured for customer access. That message deliberately does not name the setting — the
actionable detail goes to your server log instead, which names `oauth.storefrontConsentUrl`.

### The two calls your page makes

| Call | Credential | Purpose |
|---|---|---|
| `GET {issuer}/mcp/oauth/authorization-request?request_token=…` | None | Find out who is asking |
| The `authorizeMcpClient` mutation on the Shop API | The shopper's ordinary Shop API session | Record the decision |

**The lookup** needs no credential at all, which is what lets you show the request before asking anyone to sign
in. It returns:

```json
{
    "client_id": "…",
    "client_id_source": "dcr",
    "client_name": "Acme Assistant",
    "client_uri": "https://acme.example.com",
    "logo_uri": "https://acme.example.com/logo.png",
    "redirect_uri": "https://acme.example.com/callback",
    "resource": "https://my-store.example.com/mcp/shop",
    "toolset": "shop"
}
```

`client_uri` and `logo_uri` are omitted entirely when the client did not register them. `client_id_source` is
`"cimd"` when the `client_id` is a Client ID Metadata Document URL — the details above were fetched from it, so
its hostname is a verifiable identity — and `"dcr"` when the client registered itself via Dynamic Client
Registration, in which case every detail is self-asserted. Anything other than a success response means the
request token is unknown, has timed out, or has already been decided.

**The decision** is a Shop API mutation:

```graphql
mutation ApproveMcpClient($requestToken: String!, $approved: Boolean!) {
    authorizeMcpClient(requestToken: $requestToken, approved: $approved) {
        redirectUrl
    }
}
```

Send the browser to the `redirectUrl` it returns. On approval that URL hands an authorization code back to the
client; on denial it carries the refusal back instead.

The mutation is public, so **a shopper who is not signed in can still deny**. Approving is different: it needs a
signed-in customer, because the grant is attached to that customer's account. It is also refused for a user who
holds an administrator record — one person registered as both a customer and an administrator would otherwise
receive a customer-scoped token for an account with staff privileges.

The request token is single-use. It is consumed by the first decision, so a shopper who reloads the page after
approving will find the lookup fails. Treat that as an expired flow: your page cannot restart something the
client began, so the only useful thing it can say is "go back to your assistant and connect again".

### The decision flow

```text
request_token from the page URL
  │
  ▼
GET /mcp/oauth/authorization-request?request_token=…          (no credential needed)
  │
  ├─ unknown, expired or already decided
  │    → "This request has expired. Go back to your assistant and connect again."
  │
  ▼
Is client_id your own assistant's?
  │
  ├─ yes ── signed in? ── no  → send to your login page, return to this URL
  │                       └─ yes → authorizeMcpClient(approved: true) → redirect
  │                                (no consent screen — the shopper chose this assistant)
  │
  └─ no  → show "<name> wants access to your account", with Approve and Deny
             ├─ Deny ──── authorizeMcpClient(approved: false) → redirect  (no sign-in needed)
             └─ Approve ─ signed in? ── no  → send to your login page, return to this URL
                                        └─ yes → authorizeMcpClient(approved: true) → redirect
```

### Rules your page must follow

**Send your channel token if your store has more than one sales channel.** The mutation has no channel argument.
It takes the channel from the request, exactly like every other Shop API call.

Call it without a channel token and Vendure resolves the request to the **default channel**. Two things then go
wrong:

- The authorization is recorded against the default channel, so the client's tools work there rather than in the
  channel the shopper was browsing.
- The shopper's **own active channel changes to the default too**. Vendure stores the resolved channel on the
  session on any authenticated Shop API request, so a consent page that forgets the token moves the shopper out
  of the channel they were in. That is not something this mutation does, but it is the effect.

So send the token — the `vendure-token` header by default — on the mutation, exactly as the rest of your
storefront does. On a single-channel store there is nothing to do. The lookup call never needs it, because it
reads nothing channel-specific.

**Show the request before the login.** The lookup needs no credential precisely so that you can. A shopper
should be able to see what they are allowing before typing a password.

**Compare the client id, never the name.** Registration is open: anything can register and pick its own
`client_name`, so the name is a value a stranger chose. Present it as unverified rather than as an established
identity, or a shopper can be shown "Acme Shoes Official Assistant" belonging to somebody else. Skipping the
screen for your own assistant is unaffected by this, because that comparison is on `client_id`, which the server
generated.

**Allow your storefront's origin in `apiOptions.cors`.** A page running in the browser reads the lookup endpoint
and posts to the Shop API from your storefront's origin, so that origin has to be permitted. It already has to
be, for every other Shop API call your storefront makes.

### Where the submission must come from

Approving acts on whatever Shop API session the request carried. Without a check, a page on another site could
trigger an approval inside a signed-in shopper's browser. One rule prevents that:

> If the request carries an `Origin` header, it must match the origin of your configured
> `oauth.storefrontConsentUrl`. If it carries no `Origin` at all, it is allowed.

That covers both ways of building the page:

- **A page rendered on your server** calls the Shop API from Node, which attaches no `Origin` header, so it
  passes.
- **A page running in the browser** always attaches `Origin` to a cross-site POST, and page code cannot suppress
  it. Your own page's origin is the consent page's origin, so it matches. A stranger's page cannot make it match.

The practical consequence, **for a page that submits from the browser**, is that
`oauth.storefrontConsentUrl` must be on the same origin as that page. If the two differ, your own page's
submissions are refused. A page that submits from your server is not affected, because it sends no `Origin` for
the rule to compare. This is usually met first as a preview or staging deployment: if its origin differs from
the address configured in `oauth.storefrontConsentUrl`, its approvals are refused until the setting is updated
to match.

### A reference implementation

Two files. The first holds the calls, so it works the same whether your page renders in the browser or on your
server; the second is the page itself.

```ts title="src/mcp-consent/mcp-consent.ts"
// Where your Vendure server lives, and where its Shop API is.
const VENDURE_URL = 'https://my-store.example.com';
const SHOP_API_URL = `${VENDURE_URL}/shop-api`;

// The channel this storefront serves. Required if your store has more than one sales
// channel; on a single-channel store you can remove it and the header below.
const CHANNEL_TOKEN = 'my-channel-token';

// The client id your own assistant registered, if you have one, so its requests can be
// approved without showing a screen. Leave it empty if every client that reaches this
// page belongs to somebody else.
export const OWN_CLIENT_ID = '';

export interface AuthorizationRequest {
    client_id: string;
    client_name: string;
    /** Absent when the client did not register one. */
    client_uri?: string;
    /** Absent when the client did not register one. */
    logo_uri?: string;
    redirect_uri: string;
    resource: string;
    toolset: 'shop' | 'admin';
}

/**
 * Reads the pending request. Needs no credential, so this works before the shopper has
 * signed in. Returns 'expired' for a token that is unknown, timed out or already decided.
 */
export async function loadAuthorizationRequest(
    requestToken: string,
): Promise<AuthorizationRequest | 'expired'> {
    const url = new URL('/mcp/oauth/authorization-request', VENDURE_URL);
    url.searchParams.set('request_token', requestToken);
    const response = await fetch(url);
    return response.ok ? ((await response.json()) as AuthorizationRequest) : 'expired';
}

/** Records the decision and returns the URL to send the browser to next. */
export async function submitDecision(requestToken: string, approved: boolean): Promise<string> {
    const data = await shopApi<{ authorizeMcpClient: { redirectUrl: string } }>(
        `mutation ApproveMcpClient($requestToken: String!, $approved: Boolean!) {
            authorizeMcpClient(requestToken: $requestToken, approved: $approved) {
                redirectUrl
            }
        }`,
        { requestToken, approved },
    );
    return data.authorizeMcpClient.redirectUrl;
}

/** True when the shopper has a signed-in Shop API session. */
export async function isSignedIn(): Promise<boolean> {
    const data = await shopApi<{ activeCustomer: { id: string } | null }>(
        '{ activeCustomer { id } }',
    );
    return data.activeCustomer !== null;
}

async function shopApi<T>(query: string, variables?: Record<string, unknown>): Promise<T> {
    const response = await fetch(SHOP_API_URL, {
        method: 'POST',
        // Sends the shopper's Vendure session cookie. If your storefront authenticates with
        // a bearer token instead, set `Authorization: Bearer <token>` here as it does
        // everywhere else.
        credentials: 'include',
        headers: {
            'content-type': 'application/json',
            // The mutation takes the channel from the request. Omit this and the
            // authorization is recorded against the default channel.
            'vendure-token': CHANNEL_TOKEN,
        },
        body: JSON.stringify({ query, variables }),
    });
    const payload = (await response.json()) as {
        data?: T;
        errors?: Array<{ message: string }>;
    };
    if (payload.errors?.length) {
        throw new Error(payload.errors[0].message);
    }
    return payload.data as T;
}
```

```tsx title="src/mcp-consent/McpConsentPage.tsx"
import { useEffect, useState } from 'react';

import {
    AuthorizationRequest,
    isSignedIn,
    loadAuthorizationRequest,
    OWN_CLIENT_ID,
    submitDecision,
} from './mcp-consent';

type PageState =
    | { status: 'busy' }
    | { status: 'expired' }
    | { status: 'decide'; request: AuthorizationRequest };

export function McpConsentPage() {
    const requestToken = new URLSearchParams(window.location.search).get('request_token') ?? '';
    const [state, setState] = useState<PageState>({ status: 'busy' });

    async function decide(approved: boolean) {
        // Denying never requires a signed-in shopper, so only check before approving.
        if (approved && !(await isSignedIn())) {
            // Come back to this exact URL afterwards — the request token is part of it.
            const returnTo = encodeURIComponent(window.location.href);
            window.location.assign(`/login?redirectTo=${returnTo}`);
            return;
        }
        setState({ status: 'busy' });
        window.location.assign(await submitDecision(requestToken, approved));
    }

    useEffect(() => {
        void (async () => {
            // Load the request before anything else, so the shopper can see what is being
            // asked even if they still have to sign in.
            const request = await loadAuthorizationRequest(requestToken);
            if (request === 'expired') {
                setState({ status: 'expired' });
                return;
            }
            // Your own assistant needs no screen: the shopper already chose to use it.
            // Compare the id the server generated, never the name the client chose.
            if (OWN_CLIENT_ID && request.client_id === OWN_CLIENT_ID) {
                await decide(true);
                return;
            }
            setState({ status: 'decide', request });
        })();
    }, [requestToken]);

    if (state.status === 'busy') {
        return <p>One moment…</p>;
    }
    if (state.status === 'expired') {
        return <p>This request has expired. Go back to your assistant and connect again.</p>;
    }

    const { request } = state;
    return (
        <section>
            <h1>Allow access to your account?</h1>
            <p>
                An application calling itself <strong>{request.client_name}</strong> wants to use your
                account on this store. We have not verified that name.
            </p>
            <p>
                If you approve, it will be able to browse the catalogue, manage your cart and see your
                orders as you. It will be sent back to{' '}
                <strong>{new URL(request.redirect_uri).origin}</strong>.
            </p>
            <button onClick={() => decide(true)}>Approve</button>
            <button onClick={() => decide(false)}>Deny</button>
        </section>
    );
}
```

### Letting shoppers see and revoke their connections

Approving a grant here is not the only Shop API surface: a signed-in customer can also list and end their own
grants, for a "connected assistants" page in your account area. `activeMcpClientGrants` returns the customer's
active grants (id, client name, and the timestamps shown above), across every channel they were made on — the
consent belongs to the person, not the storefront they happened to use. `revokeMcpClientGrant(id: ID!)` ends one
of those grants the same way the dashboard's admin-side revoke does: the grant's tokens stop working immediately
and its dedicated Vendure session is deleted. Both operations require a signed-in customer and only ever act on
that customer's own grants.

## Operational notes

These apply to every deployment described on this page, and to both assistant guides.

**Raise `rateLimits.perClient` if you run your own assistant.** The per-client limit is counted per OAuth client
record, and one record serves every grant issued for a given assistant name. So with a first-party assistant the
default of **120 requests per minute is a ceiling for your whole store's assistant traffic**, not a per-shopper
allowance. It was sized for one third-party client acting for one person. The per-session limit is separate: it is
counted per grant, and caps a single conversation at 60 requests per minute.

```ts title="src/vendure-config.ts"
McpPlugin.init({
    rateLimits: {
        perClient: { rpm: 3000 },
    },
});
```

**Give the cache a backend that only evicts on time.** Rate-limit counters live in Vendure's `CacheService`.
The default `InMemoryCacheStrategy` holds 10,000 entries and drops the oldest when it is full, sharing that space
with everything else Vendure caches. A busy store can therefore evict a counter before its one-minute window is
up, which silently resets the limit at exactly the moment it matters. A first-party assistant adds steady traffic,
so it makes that more likely. `RedisCachePlugin` expires entries by time and has no entry cap:

```ts title="src/vendure-config.ts"
import { RedisCachePlugin } from '@vendure/core';

plugins: [
    RedisCachePlugin.init({
        redisOptions: { host: 'localhost', port: 6379 },
    }),
];
```

It also gives you one shared set of counters across app instances, instead of one set per instance.

**Handle a refusal rather than failing.** Surface a "try again in a moment" message to the person chatting.
A refusal arrives in one of two shapes, so handle both:

- **Before a tool runs** — during the client's own setup calls — it is a protocol error carrying
  `data.retryAfterSeconds` and `data.scope`.
- **Once a tool has started** — it is an ordinary failed tool result, with a text message and no structured
  retry hint at all.

Read the retry hint defensively: treat a missing value as "wait a few seconds". Do not branch on the numeric
error code, and do not assume the HTTP status — a refusal is already 429 today when the request expected no
reply, and 200 when there is a request to answer, so that `error.data` survives a client that discards non-2xx
bodies. The error code, meanwhile, is moving out of the range the 2026-07-28 protocol revision reserves.
