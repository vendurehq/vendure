The plugin ships **42 built-in tools**: **19 on the shop toolset** and **23 on the admin toolset**. This page
groups them by area and explains the model they follow. It is not exhaustive on every input field — the live
`tools/list` response for your configuration is the authoritative set, because it already accounts for
permissions, tool toggles, and exposure mode.

## The model

**Toolsets.** Every tool belongs to `shop` or `admin`, which decides the endpoint that serves it
(`/mcp/shop` or `/mcp/admin`) and the permissions it is checked against.

**Permissions (OR).** A tool declares one or more [`Permission`](/reference/typescript-api/common/permission/)
values and the caller needs *any one* of them. Shop tools use `Public` (anonymous) or `Authenticated`
(signed-in customer); admin tools use fine-grained permissions such as `ReadOrder` or `UpdateProduct`.

### How tool safety is derived

Each tool declares a single `behavior`, one of:

- **readonly** — changes nothing.
- **mutating** — writes data and runs immediately. This is the default when `behavior` is omitted.
- **destructive** — writes data and requires the confirmation round-trip below before running.

The declared behavior drives the MCP annotations an agent sees (`readOnlyHint`, `destructiveHint`).

### Destructive confirmation

A **destructive** tool is gated: the registry advertises an optional `confirm` parameter, and a call without
`confirm: true` returns a non-error prompt describing the action instead of running it. The agent must re-call
with confirmation. Five built-in tools are destructive:

| Tool | Toolset |
|---|---|
| `place_order` | **shop** |
| `adjust_stock` | admin |
| `cancel_order` | admin |
| `refund_order` | admin |
| `update_order_state` | admin |

Note that `place_order` is on the **shop** toolset — the shop tools are *not* confirmation-free. Placing an order
is a real-money action, so it is gated like the destructive admin tools.

### Tool toggles

Administrators can enable or disable any individual tool (via the dashboard MCP Server overview, or the
`setMcpToolEnabled` mutation, gated by `UpdateMcpServer`). A disabled tool disappears from `tools/list` and
cannot be called. This is the primary lever for scoping what an agent can do.

## Tool exposure: direct vs discovery

`toolExposure` controls what `tools/list` returns.

**`direct` (default)** lists every permitted, enabled tool. Prefer it: modern agents and hosts do their own
tool-search, and listing tools normally is what lets that work. Scope an agent by disabling tools, not by hiding
the list.

**`discovery` (opt-in)** replaces the full list with exactly two meta-tools:

- `search_tools({ query, limit? })` — returns the tools whose name, title, description, or author-supplied
  keywords best match the query (ranked with BM25), each with its input schema. `query` is required; passing it as
  an empty string skips ranking and returns the first `limit` tools by name (`limit` defaults to 10 and is clamped
  to 50), so it is a sample of what is available rather than the full list.
- `execute_tool({ name, arguments })` — runs a tool found via `search_tools`, validating `arguments` against that
  tool's schema exactly as a direct call would.

Reach for discovery only when the full list is a problem — a host with a low tool cap (42 tools exceeds some
clients' limits), or a model with no built-in tool search (older Claude/GPT, Gemini, Grok, GLM, and most
open-source models). It is a compatibility escape hatch, not the recommended default.

:::note
Discovery keeps the same permission and confirmation rules as direct mode; it only changes how tools are listed
and invoked, never what a caller is allowed to do.
:::
