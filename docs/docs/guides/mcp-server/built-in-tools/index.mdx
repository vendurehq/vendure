The plugin ships 41 built-in tools: 18 on the shop toolset and 23 on the admin toolset. This page groups them by
area and explains the model they follow. It is not exhaustive on every input field. The live `tools/list`
response for your configuration is the authoritative set: it already accounts for permissions, tool toggles, and
exposure mode.

## How the tools are organized

- **Toolset.** Every tool belongs to `shop` or `admin`, which decides the endpoint that serves it
  (`/mcp/shop` or `/mcp/admin`) and the permissions it is checked against.
- **Permissions.** A tool declares one or more [`Permission`](/reference/typescript-api/common/permission/)
  values with OR semantics: the caller needs any one of them. Shop tools use `Public` (anonymous) or
  `Authenticated` (signed-in customer). Admin tools use fine-grained permissions such as `ReadOrder` or
  `UpdateProduct`.

### How tool safety is derived

Each tool declares a single `behavior`, one of:

- **readonly** — changes nothing.
- **mutating** — writes data and runs immediately. This is the default when `behavior` is omitted.
- **destructive** — writes data and requires the confirmation round-trip below before running.

The declared behavior drives the MCP annotations an agent sees: `readOnlyHint` and `idempotentHint` are true for
`readonly` tools, and `destructiveHint` is true for `destructive` tools.

### Destructive confirmation

A destructive tool is gated: the registry advertises an optional `confirm` parameter. A call without
`confirm: true` returns a non-error prompt describing the action instead of running it. The agent must re-call
with confirmation. Five built-in tools are destructive:

| Tool | Toolset |
|---|---|
| `place_order` | **shop** |
| `adjust_stock` | admin |
| `cancel_order` | admin |
| `refund_order` | admin |
| `update_order_state` | admin |

`place_order` sits on the shop toolset, so the shop tools are not confirmation-free. Placing an order is a
real-money action, and it is gated like the destructive admin tools.

### Tool toggles

Administrators can enable or disable any individual tool, from the dashboard MCP Server overview or through the
`setMcpToolEnabled` mutation (gated by `UpdateMcpServer`). A disabled tool disappears from `tools/list` and
cannot be called. Tool toggles are the primary lever for scoping what an agent can do.

## How prices are returned

Prices on products, variants, orders and shipping quotes appear twice. The plain field is a whole number in the
currency's smallest unit, which is what Vendure stores and what you should use for any calculation. The field
whose name ends in `Decimal` is the same amount written out with the decimal point in the right place. Show that
one to a shopper, or hand it to a language model.

```json
{
  "price": 20999,
  "priceDecimal": "209.99",
  "priceWithTax": 25199,
  "priceWithTaxDecimal": "251.99",
  "currencyCode": "USD"
}
```

The number of decimal places comes from your store's `moneyStrategy.precision` setting, which defaults to 2. It
is one setting for the whole store rather than one per currency. A store selling in currencies with different
numbers of decimal places handles that itself.

A shipping quote carries no currency of its own, so `get_eligible_shipping_methods` takes the currency from the
cart the quote was calculated for. Anything a shipping calculator attached to the quote under `metadata` or
`customFields` is returned unchanged alongside these fields.

## Shop tools

### Cart & Checkout

| Tool | Safety | Permission | Description |
|---|---|---|---|
| `add_to_cart` | mutating | Public | Add an item to the active cart, by variant ID or by product ID |
| `update_cart_line` | mutating | Public | Update the quantity of a cart line |
| `remove_from_cart` | mutating | Public | Remove a line from the active cart |
| `get_cart` | readonly | Public | Get the active cart |
| `apply_coupon_code` | mutating | Public | Apply a coupon code to the cart |
| `remove_coupon_code` | mutating | Public | Remove a coupon code from the cart |
| `set_checkout_addresses` | mutating | Public | Set the cart shipping address, billing address, or both in one call |
| `set_shipping_method` | mutating | Public | Set the cart shipping method |
| `get_eligible_shipping_methods` | readonly | Public | List shipping methods eligible for the cart |
| `get_eligible_payment_methods` | readonly | Public | List payment methods eligible for the cart |
| `place_order` | **destructive** | Public | Move the cart to the payment stage if needed, then add payment. Answers with a status |

Cart tools use an existing cart's currency. A cart started through `add_to_cart` uses the channel's default currency.

`add_to_cart` takes exactly one of `variantId` or `productId`. Product IDs and variant IDs are separate numbering
sequences that overlap. A product ID used where a variant ID belongs would resolve to a real but unrelated
variant, and put the wrong item in the cart. Given a `productId` for a product with several variants, the tool
adds nothing. It returns an error listing each variant with its ID, so the caller can retry with the right one.
Use `get_product` to get variant IDs in the first place.

`set_checkout_addresses` takes `shippingAddress`, `billingAddress`, and `billingSameAsShipping`, in any
combination except these two: a call with none of them is refused, and so is `billingAddress` together with
`billingSameAsShipping`. `billingSameAsShipping: true` copies the shipping address into the billing address,
taking it from `shippingAddress` in the same call or, failing that, from the shipping address already on the
cart; with neither, the call is refused. When the call writes both addresses it does so in one database
transaction, so a rejected billing address (an unknown country code, say) leaves the shipping address as it
was too.

A new shipping address can make the shipping method the shopper already chose ineligible. Vendure then
swaps the cart's shipping line to the cheapest method that is still eligible, or drops the line when none is.
It does either without reporting it, so the tool reports it instead: the response carries
`shippingMethodChanged: true` and a `message` saying which of the two happened, and `order.shippingLines`
shows the current state. A response without `shippingMethodChanged` means the chosen method survived the
change.

`place_order` answers `status: "placed"` with the order when the store marks the order as placed. It answers
`status: "awaiting_payment"` with the order and a `message` when the payment went through but the store did not
mark the order as placed, for example a payment that covers only part of the total. In that case the order stays
in `ArrangingPayment` and the cart tools refuse changes until the order is paid in full. Every order returned by
`place_order`, `get_cart`, `get_order`, `list_my_orders` and the admin `get_order` and `list_orders` includes
`payments`, each carrying `state`, `amount`, `amountDecimal`,
`transactionId`, `errorMessage` and `publicMetadata`. `publicMetadata` is the `public` key of the payment's
metadata, the same part the Shop API shows a customer, so anything the handler stored for itself is not
returned. Every order also carries `shippingWithTax` (with its `Decimal` twin) and `shippingLines`, one
entry per shipping line with its `shippingMethodId` and `priceWithTax`. An empty `shippingLines` array
means the cart has no shipping method chosen.

Every order includes `couponCodes` and `discounts`, with discounts grouped by promotion. Discount amounts are negative and include both standard and `Decimal` values.
A valid coupon does not always reduce the cart price. It may appear in `couponCodes` without changing the total or `discounts`, so compare these fields with the previous cart before reporting a discount.
Orders returned with Vendure errors, such as insufficient stock, have the same shape as successful order results.

### Filtering and paging admin lists

Every list tool takes `limit` (a whole number from 1 to 100, defaulting to 25) and `offset`. A value outside
that range is refused with a validation error naming the field, so a call for 0 rows or 1000 rows is refused
instead of returning every row in the channel.
The cap of 100 belongs to the MCP tools; it is deliberately stricter than the Admin API's `adminListQueryLimit`,
which defaults to 1000, because a tool result has to fit in a model's context.

`list_products`, `list_orders` and `list_customers` also take a `filter` object. Its keys are fields and its
values are operator objects, and every condition in it has to hold for a record to be returned. There is no
way to express "either or": for that, call the tool twice.

| Value type | Operators |
|---|---|
| String | `eq`, `contains`, `in` (an array of exact values) |
| Date | `before`, `after`, each an ISO 8601 date-time such as `2026-08-25T12:00:00Z` |
| Number | `eq`, `gte`, `lte` |
| Boolean | `eq` |

`contains` is case-insensitive on Postgres; on other databases it follows the collation of the column.

| Tool | Filterable fields |
|---|---|
| `list_products` | `name`, `slug`, `sku` (matches any of the product's variants), `enabled`, `updatedAt` |
| `list_orders` | `code`, `state`, `active`, `customerLastName`, `orderPlacedAt`, `updatedAt`, `totalWithTax` |
| `list_customers` | `emailAddress`, `firstName`, `lastName`, `phoneNumber`, `postalCode` (matches any of the customer's addresses), `createdAt` |

Finding the orders that have been sitting at payment since before noon:

```json
{
  "filter": {
    "state": { "eq": "ArrangingPayment" },
    "updatedAt": { "before": "2026-08-25T12:00:00Z" }
  }
}
```

`totalWithTax` is a whole number in the currency's smallest unit, like every other price these tools return.

## Tool exposure: direct vs discovery

`toolExposure` controls what `tools/list` returns.

### `direct` (default)

Lists every permitted, enabled tool. Prefer it: modern agents and hosts do their own tool search. Scope an agent
by disabling tools, not by hiding the list.

### `discovery` (opt-in)

Replaces the full list with exactly two meta-tools.

`search_tools({ query, limit? })` returns the tools that best match the query, ranked with BM25 over each tool's
name, title, description, and author-supplied keywords. Each result includes the tool's input schema. `query` is
required. An empty string skips ranking and returns the first `limit` tools by name, as a sample of what is
available rather than the full list. `limit` defaults to 10 and is clamped to between 1 and 50.

`execute_tool({ name, arguments })` runs a tool found via `search_tools`. It validates `arguments` against that
tool's schema exactly as a direct call would.

Reach for discovery only when the full list is a problem:

- A host with a low tool cap: 41 tools exceeds some clients' limits.
- A model with no built-in tool search: older Claude and GPT models, Gemini, Grok, GLM, and most open-source
  models.

Discovery is a compatibility escape hatch, not the recommended default.

:::note
Discovery keeps the same permission and confirmation rules as direct mode. It changes how tools are listed and
invoked, never what a caller is allowed to do.
:::
