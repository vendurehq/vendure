### shopAccess

<MemberInfo kind="property" type={`'disabled' | 'authenticated' | 'anonymous'`} default={`'anonymous'`}   />

Controls HTTP access to the `/mcp/shop` endpoint and the shop toolset.

- `'anonymous'` (default): the endpoint accepts anonymous callers as well as
  OAuth-authenticated customers.
- `'authenticated'`: the endpoint requires an OAuth Bearer token. Token-less
  requests receive a 401 with the standard auth challenge.
- `'disabled'`: the endpoint responds 404 and customer OAuth authorization
  requests are refused.

In-process tool execution via [McpToolExecutionService](/reference/core-plugins/mcp-plugin/mcp-tool-execution-service#mcptoolexecutionservice) is not affected.

### localTrust

<MemberInfo kind="property" type={`boolean`} default={`true`}  since="4.0.0"  />

Lets the Vendure CLI's own tools, `vendure mcp` and `vendure api admin`, call this server
without OAuth while it runs as a local dev server. Local trust is full superadmin access on
the developer's machine, on `POST /mcp/admin` and on the Admin API path. It never applies
to `/mcp/shop`, which keeps its `shopAccess`.

It only turns on when all of these hold at startup:

- this option is not `false`;
- the server process received a per-run secret from the CLI in the
  `VENDURE_LOCAL_TRUST_SECRET` environment variable. The plugin deletes it from the
  environment once it has read it;
- the CLI's state file holds the same secret. On macOS and Linux it is
  `.vendure/devserver.json` in the project directory, and must have mode 0600 and be owned by
  the user the server runs as. On Windows it is
  `%LOCALAPPDATA%\Vendure\devserver\<hash>.json` in the user profile, and its real path must
  be under the current user's `%LOCALAPPDATA%`. Without `LOCALAPPDATA`, local trust stays
  off on Windows. Windows has no file modes, so the file is protected only by the permissions
  of the `%LOCALAPPDATA%` directory, which by default only the user, SYSTEM and administrators
  can read. The server does not check those permissions.

The server then logs a warning that local trust is on. A request presenting the secret as
`Authorization: Bearer <secret>` is accepted only from a loopback socket address, with a
`Host` header of `localhost`, `127.0.0.1` or `[::1]`, no `Origin` header, and none of the
forwarded headers `X-Forwarded-For`, `X-Forwarded-Host`, `Forwarded`, `X-Real-IP` or `Via`.
So a request through a proxy, or from a browser, is refused.

To accept the secret on the Admin API, the plugin adds `'bearer'` to
`authOptions.tokenMethod` when it is missing, and logs that it did so. That change affects
the whole server: every Admin and Shop API request may then authenticate with a bearer
token.

On the Admin API, the secret maps to one session per run, which the plugin deletes when the
server stops, and at the next start after a crash. A `logout` mutation sent with the secret
fails, because that session belongs to no authentication strategy.

Set it to `false` on any server that runs outside a developer's machine.
