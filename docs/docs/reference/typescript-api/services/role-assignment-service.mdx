## RoleAssignmentService

<GenerationInfo sourceFile="packages/core/src/service/services/role-assignment.service.ts" sourceLine="69" packageName="@vendure/core" since="4.0.0" />

Contains methods relating to [RoleAssignment](/reference/typescript-api/entities/role-assignment#roleassignment) entities — the `(user, role, channel)`
triples which grant a User a Role's permissions on a specific Channel.

The actor-made writes are `assign` and `remove`. Both authorize every pair
through `RoleService.canGrant`, and the filtered reads (`findAll`,
`getGrantableAssignmentsForUser`) apply the same predicate, so an actor sees exactly
the assignments they may change. Beneath them sit the unauthorized row primitives
`createAssignments`, `deleteAssignments` and `removeAllAssignmentsForUser`,
for writes which have no actor to check against. Every one of these publishes a
[RoleAssignmentEvent](/reference/typescript-api/events/event-types#roleassignmentevent) for the pairs it actually changed.

The SuperAdmin Role is stored as a single row on the default Channel (see
[RoleAssignment](/reference/typescript-api/entities/role-assignment#roleassignment)). `assign` and `remove` rewrite a SuperAdmin pair on any
Channel to that row, so there is never more than one SuperAdmin row per User.

All writes go through entity-based repository operations so that [SessionService](/reference/typescript-api/services/session-service#sessionservice)'s
entity subscriber observes them and evicts the affected User's cached sessions — permission
changes therefore take effect on the User's next request.

### isSoleSuperAdminHolder

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>) => Promise<boolean>`}  since="4.0.0"  />

Whether the given User is the only non-deleted Administrator holding the SuperAdmin
Role. There must always be one, otherwise full administration through the API is no
longer possible: `remove` and the Administrator soft-delete both refuse to break
this.

Takes a write lock on the SuperAdmin Role row before counting, held until the
surrounding transaction commits. Two SuperAdmins removing or deleting each other at
the same time would otherwise both count two holders and leave none. The count is a
locking read too: under REPEATABLE READ (the MySQL and MariaDB default) a plain read
after the lock still sees the snapshot taken at the transaction's first read, so it
would miss the other transaction's committed write. Call it inside the transaction
which performs the write. On SQLite locks are not supported; SQLite serializes writes
itself.
### assign

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>, pairs: <a href='/reference/typescript-api/services/role-assignment-service#rolechannelpair'>RoleChannelPair</a>[]) => Promise<<a href='/reference/typescript-api/entities/role-assignment#roleassignment'>RoleAssignment</a>[]>`}  since="4.0.0"  />

Grants the User each of the given `(roleId, channelId)` pairs. The active user must be
permitted to grant every pair (`RoleService.canGrant`), pairs the User already
holds included; those are then left as-is and not reported, so a write which changes
nothing publishes nothing. A SuperAdmin pair on any Channel is stored as the single
default-channel row (see [RoleAssignment](/reference/typescript-api/entities/role-assignment#roleassignment)): the [RolePermissionResolver](/reference/typescript-api/auth/role-permission-resolver#rolepermissionresolver)
derives SuperAdmin access on every Channel from that one row.

Publishes an `assigned` [RoleAssignmentEvent](/reference/typescript-api/events/event-types#roleassignmentevent) for the pairs actually added, and
returns the User's assignments after the write.
### remove

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>, pairs: <a href='/reference/typescript-api/services/role-assignment-service#rolechannelpair'>RoleChannelPair</a>[]) => Promise<<a href='/reference/typescript-api/entities/role-assignment#roleassignment'>RoleAssignment</a>[]>`}  since="4.0.0"  />

Revokes each of the given `(roleId, channelId)` pairs from the User. The rule is the
same as for `assign`: the active user must be permitted to grant every pair
(`RoleService.canGrant`), so what an actor may take away is exactly what they
could hand out. Pairs the User does not hold pass the same check and are then left
as-is and not reported. A SuperAdmin pair on any Channel addresses the single
default-channel row, mirroring `assign`, so removing SuperAdmin on any Channel
removes it everywhere. The sole SuperAdmin cannot have the SuperAdmin Role taken away.

Publishes a `removed` [RoleAssignmentEvent](/reference/typescript-api/events/event-types#roleassignmentevent) for the pairs actually removed, and
returns the User's assignments after the write.
### assertManageableSubject

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>) => Promise<void>`}  since="4.0.0"  />

Asserts that the User may be the target of an actor-made `assign` or `remove`.
The target must be a non-deleted Administrator, or the User of a non-deleted ApiKey which
belongs to the active Channel, in which case the active user must also hold
`UpdateApiKey` there. Any other User, a Customer's User included, is reported as not
found, so that admin Roles cannot be granted to it and its existence is not disclosed.

`assign` and `remove` do not call this themselves: the services which create
Administrators and ApiKeys assign Roles to a User whose entity they are still writing.
### replaceRolesOnChannel

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>, roleIds: <a href='/reference/typescript-api/common/id#id'>ID</a>[], channelId: <a href='/reference/typescript-api/common/id#id'>ID</a> = ctx.channelId) => Promise<void>`}   />

Implements the deprecated `roleIds` inputs of the administrator and API-key mutations,
which replace the User's Roles on one Channel. The replacement is applied as deltas:
Roles in `roleIds` not yet held on the Channel are granted through `assign`,
Roles held there but absent from `roleIds` are revoked through `remove`, so every
changed pair is authorized by `RoleService.canGrant`. A `roleIds` list which
omits a pair the active user may not revoke fails rather than being applied in part.

The `roleIds` inputs are deprecated since 4.0.0 in favor of the `assignRolesToUser` and
`removeRolesFromUser` mutations. Remove this method in v5.0.0 together with them.
### createAssignments

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>, pairs: <a href='/reference/typescript-api/services/role-assignment-service#rolechannelpair'>RoleChannelPair</a>[]) => Promise<void>`}  since="4.0.0"  />

Creates a RoleAssignment for each of the given `(roleId, channelId)` pairs the User does
not already hold, and publishes one `assigned` [RoleAssignmentEvent](/reference/typescript-api/events/event-types#roleassignmentevent) for the pairs
added. Nothing is published when nothing changes.

Performs no authorization and no SuperAdmin anchoring: this is the row primitive beneath
`assign`, for writes which have no actor to check against, such as granting a User
created by an authentication strategy the Roles that strategy resolved. Actor-made
changes go through `assign`.
### deleteAssignments

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>, pairs: <a href='/reference/typescript-api/services/role-assignment-service#rolechannelpair'>RoleChannelPair</a>[]) => Promise<void>`}  since="4.0.0"  />

Deletes the User's RoleAssignments matching the given `(roleId, channelId)` pairs, and
publishes one `removed` [RoleAssignmentEvent](/reference/typescript-api/events/event-types#roleassignmentevent) for the pairs removed. Pairs the User

### removeAllAssignmentsForUser

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, userId: <a href='/reference/typescript-api/common/id#id'>ID</a>) => Promise<void>`}  since="4.0.0"  />

Deletes every RoleAssignment of the User across all Channels, and publishes one
`removed` [RoleAssignmentEvent](/reference/typescript-api/events/event-types#roleassignmentevent) for them. Nothing is published for a User
holding no assignments.

Performs no authorization and no sole-SuperAdmin guard: this is the primitive behind
the Administrator and API-Key soft-deletes, which must clear the rows of the deleted
User. Left in place, those rows would keep counting towards the Channels a Role is
assigned on (see [RoleService](/reference/typescript-api/services/role-service#roleservice)) and so keep gating the Role for live administrators.
### removeAllAssignmentsOnChannel

<MemberInfo kind="method" type={`(ctx: <a href='/reference/typescript-api/request/request-context#requestcontext'>RequestContext</a>, channelId: <a href='/reference/typescript-api/common/id#id'>ID</a>) => Promise<void>`}  since="4.0.0"  />

Deletes every RoleAssignment on the given Channel, and publishes one `removed`
[RoleAssignmentEvent](/reference/typescript-api/events/event-types#roleassignmentevent) per affected User. Call it before the Channel row is
deleted: the foreign key would otherwise cascade the rows away with no event and no
eviction of the affected Users' cached sessions.

Performs no authorization and no sole-SuperAdmin guard: this is the primitive behind
the Channel delete. The SuperAdmin row lives on the default Channel, which cannot be
deleted.
