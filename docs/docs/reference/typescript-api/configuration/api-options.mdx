The ApiOptions define how the Vendure GraphQL APIs are exposed, as well as allowing the API layer
to be extended with middleware.

```ts title="Signature"
interface ApiOptions {
    hostname?: string;
    port: number;
    adminApiPath?: string;
    shopApiPath?: string;
    shopListQueryLimit?: number;
    adminListQueryLimit?: number;
    adminApiValidationRules?: Array<(context: ValidationContext) => any>;
    shopApiValidationRules?: Array<(context: ValidationContext) => any>;
    channelTokenKey?: string;
    cors?: boolean | CorsOptions;
    csrfPrevention?: boolean | CSRFPreventionOptions;
    middleware?: Middleware[];
    trustProxy?: TrustProxyOptions;
    apolloServerPlugins?: ApolloServerPlugin[];
    introspection?: boolean;
    includeStackInErrors?: boolean;
}
```

### cors

<MemberInfo kind="property" type={`boolean | CorsOptions`} default={`{ origin: false, credentials: true }`}   />

Set the CORS handling for the server. See the [express CORS docs](https://github.com/expressjs/cors#configuration-options).

By default no cross-origin browser requests are allowed: the server sends no
`Access-Control-Allow-Origin` header, so a browser only lets pages on the server's own origin call
the API. The Dashboard served by the `DashboardPlugin` is on that origin, so it works without any
CORS setting. A storefront, or a Dashboard dev server, on another origin needs that origin listed
in `origin`. Server-side requests, such as those from a server-rendered storefront, are not subject
to CORS.

Keep `credentials: true` when you list origins, so that cookie sessions work.

:::warning
Do not set `origin: true` outside local development. It reflects the `Origin` header of any caller
back as `Access-Control-Allow-Origin`, and together with `credentials: true` it lets any website make
cross-origin requests to your Shop and Admin APIs. If you also set `authOptions.cookieOptions.sameSite`
to `'none'`, any website can act as a logged-in user. Vendure logs a warning at startup when it
detects `origin: true` together with `credentials: true`.
:::

*Example*

```ts
const config: VendureConfig = {
  apiOptions: {
    cors: {
      origin: ['https://storefront.example.com', 'https://admin.example.com'],
      credentials: true,
    },
  },
};
```
### csrfPrevention

<MemberInfo kind="property" type={`boolean | CSRFPreventionOptions`} default={`true`}  since="3.7.3"  />

Enables Apollo Server's built-in CSRF prevention on both the Shop API and the Admin API. It is on
by default.

When enabled, Apollo rejects any request whose `content-type` is one that a browser lets an
HTML form or a simple `fetch` send without a preflight, namely
`application/x-www-form-urlencoded`, `multipart/form-data` and `text/plain`, unless the request
also carries an `Apollo-Require-Preflight` or `x-apollo-operation-name` header. Requests sent as
`application/json`, which is what all Vendure clients use for normal operations, are unaffected.

This blocks Login CSRF. Without it, a cross-site HTML form can POST
`query=mutation { login(...) }` to your API as a top-level navigation. That is not a
cross-origin request in the CORS sense, so `apiOptions.cors` does not stop it, and a
`SameSite=Lax` cookie does not stop it either, because a top-level navigation is allowed to
store a cookie with any `SameSite` value. The response sets a session cookie in the victim's
browser, and the victim continues shopping while logged in as the attacker.

Every client which uploads files to your API must send the `Apollo-Require-Preflight` header,
since multipart uploads use one of the blocked content types. `@vendure/dashboard` and
`@vendure/testing` both send it. A custom admin client built on `apollo-upload-client` does not
send it unless you add it.

The same applies to `GET` requests, which carry no content type at all: a storefront that uses
`GET` for cacheable queries must send the `Apollo-Require-Preflight` header as well.

Passing an object instead of `true` replaces the list of headers which permit an operation,
which by default is `x-apollo-operation-name` and `apollo-require-preflight`. Use this when a
client cannot be changed to send either of those: add a header the client already sends, for
example `{ requestHeaders: ['x-my-client-header', 'apollo-require-preflight'] }`, rather than
turning the protection off. Keep `apollo-require-preflight` in the list, since
`@vendure/dashboard` and `@vendure/testing` send only that header.

Setting it to `false` turns the protection off and makes Login CSRF possible for cookie
sessions, and Vendure logs a warning at startup when you do. Bearer-only deployments are not
affected by Login CSRF.

*Example*

```ts
const config: VendureConfig = {
  apiOptions: {
    // Also accept a header that a client which cannot send `Apollo-Require-Preflight` already sends
    csrfPrevention: { requestHeaders: ['x-my-client-header', 'apollo-require-preflight'] },
  },
};
```

### introspection

<MemberInfo kind="property" type={`boolean`} default={`true`}  since="1.5.0"  />

Controls whether introspection of the GraphQL APIs is enabled. For production, it is recommended to disable
introspection, since exposing your entire schema can allow an attacker to trivially learn all operations
and much more easily find any potentially exploitable queries.

**Note:** when introspection is disabled, tooling which relies on it for things like autocompletion
will not work.

*Example*

```ts
{
  introspection: process.env.NODE_ENV !== 'production'
}
```
### includeStackInErrors

<MemberInfo kind="property" type={`boolean`} default={`false`}  since="4.0.0"  />

Adds `extensions.stack` to each error which the Admin and Shop APIs return. It lists the frames
of the error's stack which point at the project's own files: those under the working directory and
not under `node_modules`, with paths relative to the working directory.

This is meant for local development only, so that a developer or a coding agent can see where an
error was thrown. The frames name the project's files and functions, so this must stay off on any
server which untrusted callers can reach, including staging servers. When it is off, no error
response carries a stack, whatever `NODE_ENV` is set to.

When the config does not set it, it is on only if the `VENDURE_INCLUDE_STACK_IN_ERRORS`
environment variable is `true` when `@vendure/core` is first imported. `vendure dev` sets that
variable for the server it starts, so stacks show in local development without a config change.
The variable must be set before the process starts: a `.env` file loaded by `dotenv` after the
import does not count. A value in the config, `true` or `false`, always wins over the variable.

*Example*

```ts
{
  // In a config file which is only used for local development
  includeStackInErrors: true,
}
```
